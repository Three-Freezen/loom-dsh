## 一、总体结论

### 1.1 判断

方案第一节对“更新后插件像没装一样”的三条机制判断是**正确且可复核**的：兼容性拦截、崩溃恢复里的“禁用第三方插件”、安装期版本拒绝，都能在 `app.asar` 中找到对应实现。因此“快照保险 + 官方兼容判定 + 文件级还原”的方向成立，交付形态选择“绿色托盘 + 同名 CLI、不做 DSH 插件”的三条理由也成立。

但方案目前是**产品意图 + 架构草图**，还不是可直接编码的实现规格。真实更新链路里有四个关键事实会让现稿失效：

1. **更新前快照的触发点太晚**：更新器只有下载完成后才把最终安装包和 `update-info.json` 放进 `pending\`；方案却把“`pending\` 出现安装包”当作最佳快照点。
2. **包级升级没有天然执行窗口**：更新器以 `--updated --force-run` 自动启动新版本，App 退出后马上又被拉起；方案设想的“监测 DSH 退出→pnpm 升级”需要用户再退出一次，不是全自动。
3. **方案里的命令入口在实际机器上跑不通**：`dsh` 不在 PATH；普通 `dsh` 明确拒绝 `--profile desktop`；必须走 `resources\runtime\cli\bin\dsh.cmd` 这个 Desktop 专用入口。
4. **恢复流程的“内置基线”不是方案以为的那三个**：桌面端恢复用的是 `WEB_PROFILE.bundles = base + web-app`，会把当前 profile 里的 `@deepseek-ai/dsh-experimental-agent-team-profile` 一并拿掉；只还原“第三方 bundle”会漏掉它。

### 1.2 风险级别

| 维度 | 级别 | 说明 |
|---|---|---|
| 诊断结论风险 | **低** | 三条机制均有源码依据；当前 profile 状态与事故痕迹一致 |
| 实现风险 | **高** | 7 个 P0 中，3 个会让自动链路直接不工作，2 个会造成错误还原，2 个会导致不可维护 |
| 数据/恢复风险 | **中高** | 若快照过期或还原冲突规则不清，可能覆盖用户更新后的新改动，或把已删插件加回来 |
| 进度风险 | **高** | “3～4 个工作日”只够做 happy path 骨架，不足以交付方案承诺的自动升级、回滚、托盘 UI 与测试 |

### 1.3 是否可进入实现

**有条件可以**，但必须先完成三件事：

1. **补齐 P0 的 7 项设计**（尤其是更新时序状态机、CLI/pnpm 入口、锁与快照一致性、恢复冲突规则）。
2. **做 1～2 天技术验证（spike）**，在虚拟机/临时 `DSH_HOME` 上验证：
   - 用 `dsh.cmd` 在 App 完全退出后完成一次真实插件升级；
   - 模拟一次恢复流程（`.bak` + bundles 重置）后完成文件级还原；
   - 抓一次真实 nightly 更新的时序，确认 `temp-*`、最终 installer、`update-info.json` 与 App 退出/重启的实际时间点。
3. **砍掉或重排首版范围**。若坚持 3～4 天，建议只做“快照 + check + 文件级还原 + 报告 + 托盘”，把策略 A 自动升级、离线包归档、回滚放到二期；不要把“自动升级”写进首版承诺。

### 1.4 工作量判断

方案把 P1 估为 1～2 天、P2 估为 2～3 天，合计 3～4 天。按方案自己承诺的范围（快照、官方 evaluator、文件级还原、策略 A、离线归档、回滚、托盘/通知、报告、设置、开机自启、深浅双主题 UI），实际至少需要：

- P1 可用版本：**5～7 个工作日**（含基础测试与 PowerShell 5.1 兼容处理）
- P2 自动升级/离线/回滚：**6～10 个工作日**（含 mock registry、失败注入、并发与崩溃恢复测试）
- 若坚持设计稿的完整托盘弹层 + 设置窗口：再加 **3～5 个工作日**（见 P1-15）

**结论：现工作量低估约 2～3 倍。** 建议要么延长排期，要么首版缩到“手动/半自动，不承诺无感”。

## 二、问题清单

### P0 阻断（必须先改方案，不能直接编码）

#### P0-1 更新前快照的触发点落在“下载完成”之后，且旧快照可能被新快照覆盖

- **问题**：
  - 方案 3.2 与 7.3 都把“`%LOCALAPPDATA%\@deepseek-aidsh-desktop-updater\pending\` 出现安装包”当作最佳快照点，并说“更新下载完成 ≈ 马上要重启安装”。
  - Electron updater 的实际顺序是：下载到 `pending\temp-<fileName>`，下载完成后 rename 成最终文件名，再写 `pending\update-info.json`（`DownloadedUpdateHelper.setDownloadedFile`）；DSH 的 `downloadUpdate` 在 `updates.download()` 返回 ready 后**立刻**调用 `updates.install()`，安装前只弹一次“安装并重启”确认框。
  - 因此，看到**最终** installer 或 `update-info.json` 时，用户可能几秒内就点确认；含插件包归档的 full snapshot（profile 约 58.6 MB）可能来不及完成。真正有提前量的是 `temp-deepseek-harness-*.exe` 出现在下载开始时，但方案没有把它作为触发点。
  - 当前 `pending\` 里已经有一份 293 MB 的 0.2.2-rc.1 安装包和 `update-info.json`（2026-11-07），说明“文件出现”不是一次性事件；按“出现即快照”会反复误触发，或者永远认为“更新待安装”。
  - 方案 3.2 又说“每次 App 启动后 `snapshot --auto`，有变化才写新快照”。更新后首次启动时 profile 可能已经被兼容性拦截或恢复流程改坏；如果这时先写新快照，就会把“最后一份好快照”覆盖成“坏状态快照”。方案没有“冻结 pre-update 快照”的规则。
- **为什么重要**：
  - 快照是整个方案唯一的恢复源。快照抓晚了或抓的是更新后的坏状态，后面的 check/restore/策略 A 全部没有意义。
  - 旧 `pending` 的存在还会导致托盘长期显示“待更新/待处理”，或每 30 分钟做一次全量快照，浪费磁盘和 CPU。
- **建议补充**：
  1. 定义快照触发矩阵：App 启动并稳定后；profile 文件变化后 debounce（30～60 秒）；`pending\temp-*` 出现或 `download-progress` 开始时；最终 `update-info.json` 出现时（兜底）；手动“立即快照”。
  2. 在 `state.json` 中保存 `preUpdateSnapshot` 指针与 `pendingUpdate`（目标版本、installer 文件名、sha512、检测时间）。检测到版本变化后，**先处理更新，不得自动写新快照**；只有还原/升级成功且 App 稳定后，才写新的 baseline。
  3. `pending` 去重：用 `update-info.json` 的 `sha512`/`fileName` 与当前 App 版本比较；文件名版本 ≤ 当前版本、或 `state.handledUpdate` 已记录时直接忽略。不要把“目录存在”当事件。
  4. 快照元数据同时记录 `appVersion` 与 `dshVersion`；版本比较按同名字段比较（见 P1-1）。
  5. 如要支持“更新前预下载兼容插件”，从 `temp-<fileName>` 或 `update-info.json` 解析目标版本，并把它显式传给 evaluator 的第三个参数（目标 runtime），不要用当前 runtime 预检未来版本。
- **涉及方案章节**：3.2、3.3、5.3、7.3

#### P0-2 “自动重启”与“包级操作必须 App 退出”之间没有可用窗口

- **问题**：
  - 方案 3.2/3.4/7.3 的流程是“检测版本变化 → 只读 check → 提示 → 等 App 退出（或用户确认立即还原并重启）→ 用 pnpm 升级 → 提示重新打开”。
  - 实际更新器在用户确认安装后调用 `quitAndInstall(true, true)`，NSIS 安装器带 `--updated --force-run`，安装完**立即启动新版本**。不存在“App 已退出且保持退出”的稳定窗口；如果 guard 等退出，它等到的往往是“新版本已经启动”。
  - 如果 guard 试图在安装器替换文件的那几十秒内执行 pnpm，既来不及，也可能与安装器竞争文件；如果 App 已在运行，pnpm 替换 `node_modules` 又可能破坏正在加载的 host/插件。
  - 结果：方案默认的“策略 A 自动升级”实际上不能自动完成；用户必须在新版本启动后再退出一次，guard 才能装包，然后用户再打开。方案 7.3 写“监测 DSH 进程退出（或托盘点‘立即还原/升级’引导退出）”，但没有定义如何让 App 安全退出、如何识别“完全退出”、以及用户不退出时的降级路径。
- **为什么重要**：
  - 这是“更新后最多多一次重启”承诺能否成立的核心。若用户不配合再退出一次，策略 A 永远无法执行，插件会一直处于被禁用状态。
  - 如果实现者为了“自动”去 kill App 或边运行边装包，可能造成插件目录半更新、会话数据丢失、host 崩溃，比不升级更糟。
- **建议补充**：
  1. 明确状态机：`idle → snapshotReady → updateDetected → newVersionRunning → awaitingAppExit → upgrading → verifying → idle/failed`，每个状态定义托盘文案、可用按钮、超时与重试。
  2. 明确“完全退出”的判定：`DeepSeek Harness.exe` 的所有相关进程消失（注意 DSH 关闭窗口只是缩到托盘，进程仍在），至少观察 2～3 秒稳定；不要用窗口标题/可见性判断。
  3. 不自动 kill App。提供“我已在 DSH 中退出，继续”按钮 + 自动检测；可选高级操作“强制结束”必须二次确认并提示会话风险。
  4. 说明“全自动无感”在当前 updater + `--force-run` 下不可实现；把“最多多一次重启”定义清楚：新版本自动启动一次，用户退出一次，guard 升级后启动一次。
  5. 可选优化：下载期间按目标版本预解析兼容版本，预下载到独立 staging 目录；更新后仍需一次 App 退出才能切换 `node_modules`，但可缩短装包时间。该方案要额外定义 staging 的锁、校验与清理。
- **涉及方案章节**：3.2、3.4、5.3、7.3、第六节

#### P0-3 命令、运行时与 pnpm 入口的假设不成立

- **问题**：
  - 方案 3.3/3.4/7.3 使用 `dsh plugin --profile desktop add <pkg>@<ver>`、`dsh plugin allow-version ...`。本机 `where.exe dsh` 无结果，用户 PATH 中没有 DSH；普通 `@deepseek-ai/dsh` CLI 还有 `rejectElectronProfile`，会直接报“profile desktop is managed exclusively by the Electron application”。
  - 实际可用入口是 `D:\DeepSeek\resources\runtime\cli\bin\dsh.cmd`：它设置 `ELECTRON_RUN_AS_NODE=1`，用 `DeepSeek Harness.exe --expose-internals` 调 `app.asar\dsh\node_modules\@deepseek-ai\dsh-desktop-host\lib\cli.js`，并以 `manageDesktopProfile: true` 放行 desktop profile，同时把内置 pnpm（`primary-runtime\dependencies\pnpm\bin\pnpm.mjs`）作为 package manager。
  - 方案 3.5 写“`guard-helper.mjs` 用 DSH 自带 Node 运行官方 evaluator”。`resources\runtime\bin\node.cmd` 的内容是 `"%DSH_DESKTOP_NODE_EXECUTABLE%" --expose-internals %*`，独立启动时该环境变量为空；系统 Node 又不能直接 import `app.asar` 内文件（实测 `ERR_MODULE_NOT_FOUND`）。helper 必须运行在 Electron Node 模式。
  - 方案没有说明 `dsh plugin add` 默认会写入 `^<ver>` 还是精确版本；如果写 `^`，后续 `pnpm install` 可能解析到不兼容的新版本。DSH 自己的 upgrade 路径用 `--save-exact`，guard 应保持一致。
  - 如果 guard 自己先拿 `package.json.lock`，再调用 `dsh plugin`，CLI 内部还会再拿同一把锁，形成跨进程等待/死锁（CLI 默认等 120 秒）。
- **为什么重要**：
  - 这是“写代码第一天就会踩”的问题。按方案字面实现，`dsh plugin` 命令直接失败；改用系统 pnpm 则可能用错 pnpm 版本、store、lockfile 和 registry 配置；用系统 Node 跑 helper 则 evaluator 根本加载不了。
  - 锁嵌套会导致 guard 在“看起来在执行”的状态卡 120 秒后失败，用户以为工具坏了。
- **建议补充**：
  1. 新增“安装定位器”：优先读 `config.json` 的 `installDir`；否则从运行中的 `DeepSeek Harness.exe` 路径、卸载注册表、`app-update.yml` 推断；校验 `resources\runtime\cli\bin\dsh.cmd` 和 `app.asar\dsh\package.json` 存在。
  2. 新增 `DshCli` 封装：只调用完整路径的 `dsh.cmd`（参数数组、不经过字符串拼接），显式设置/保留 `ELECTRON_RUN_AS_NODE=1`，设置超时，流式记录 stdout/stderr 与退出码；失败时回退到“`DeepSeek Harness.exe` + `--expose-internals` + `dsh-desktop-host/lib/cli.js`”。
  3. helper 只在 Electron Node 下运行脚本文件（不要用 `-e`，不要把 app.asar 路径交给系统 Node）；`node.cmd` 只能作为 dsh.cmd 内部的一部分使用。
  4. 禁止调用系统 `pnpm`；统一使用 `dsh.cmd plugin ...`，必要时加 `--save-exact`；不要自己拼 pnpm 参数去模拟 DSH 的 profile 管理，除非明确做离线 fallback 并单独测试。
  5. 锁的归属写清楚：guard 自己写 `package.json` 时持有 `package.json.lock`；调用 `dsh plugin` 前**必须释放**，由 CLI 自己加锁；整个“读—改—CLI 调用—再读”用操作 journal 串起来，不要跨进程嵌套锁。
- **涉及方案章节**：3.3、3.4、3.5、7.1、7.4

#### P0-4 快照/还原缺少一致性协议：锁、读一致性、崩溃恢复 journal 都没定义

- **问题**：
  - 方案 3.6 只说“写 profile 一律走备份 → 加锁 → 原子写”，3.1 的采集方式是“读 package.json，再逐个读 node_modules manifest”。没有定义读的时候如何避免读到 pnpm 安装到一半的状态。
  - 实际存在三套协调机制（见 1.5 第 7 条）：`<profile>\lock`（桌面端 profile 操作）、`<profile>\package.json.lock`（插件管理器/CLI 写 manifest）、`.plugin-manager\run.json`（上一次 pnpm 进程的记录，防止孤儿进程继续写）。方案只提 `package.json` 文件锁，且没有说明 guard 如何与这三者共存。
  - 没有 `state.json` 的原子写/操作 journal。guard 在“复制 package.json 后、写还原文件前”崩溃，或 pnpm 装到一半退出，下一次启动无法判断上次做到哪一步；可能重复安装、重复 bundle、或把半成品当当前状态。
  - 没有定义“快照一致性”：package.json / pnpm-lock.yaml / node_modules manifest / patch 的读取顺序、重试条件、如何判定稳定（例如连续两次读取哈希一致、且没有锁/没有活跃 run 记录）。
- **为什么重要**：
  - 快照和还原都是多文件操作。没有一致性协议，恢复出来的 profile 可能是“旧 package.json + 新 lockfile”或“bundles 有插件、node_modules 没有包”，DSH 启动时再次失败。
  - DSH 自身在启动、插件安装、恢复时都会写 profile；guard 如果不懂这些锁，就会和 DSH 互相覆盖。
- **建议补充**：
  1. 画一张锁矩阵：锁文件/持有者/典型时长/guard 的动作（等待、只读、超时、放弃）。至少包含 `profile\lock`、`package.json.lock`、`.plugin-manager\run.json`、guard 自己的单实例 mutex。
  2. 快照读协议：先等 `package.json.lock`、`run.json` 消失且 App 处于稳定状态；读 package.json + lockfile + 关键 manifest；再读一次 package.json/lockfile，哈希不变才落盘；期间任何锁出现则重试（指数退避，上限 30～60 秒）。
  3. `state.json` 原子写；每次操作写 `operationId`、阶段（snapshot/restore/upgrade/verify）、开始/结束时间、before/after 哈希、命令、退出码、备份路径。启动时发现未完成操作，先进入“恢复/回滚”流程，不要直接开新操作。
  4. 还原前把当前 profile 核心文件复制到 `restore-backup/<operationId>/`，并记录清单哈希；还原完成后再校验一次。恢复失败可一键回滚。
  5. 明确“还原过程中 App 启动了”怎么办：立即停在安全点、不要继续写；提示用户退出后重试；已写的文件保留在 restore-backup 中。
- **涉及方案章节**：3.1、3.4、3.6、7.1、7.3

#### P0-5 恢复语义会漏掉官方可选 bundle，也会把“用户主动删除”当成“丢失”加回来

- **问题**：
  - 方案 3.4 说“把快照中缺失的第三方 bundle 按原顺序插回；内置基线保持当前值”。但恢复流程重置的是 `WEB_PROFILE.bundles = ["@deepseek-ai/dsh-base", "@deepseek-ai/dsh-web-app"]`，当前 profile 里还有 `@deepseek-ai/dsh-experimental-agent-team-profile`（官方可选 bundle，用户 11-07 在插件管理器里启用过）。它不是“第三方”，按方案不会还原，用户会以为“恢复完成”，但 agent-team 功能没了。
  - 恢复流程 `sanitizeProfile` 是把 `cordis.patch.yml` **rename** 成 `cordis.patch.yml.bak-<毫秒时间戳>`，不是复制；下一次启动 `applyRelease` 会通过 `initProfile` 重新创建一个空模板。方案 3.4 说“当前文件为空/缺失才恢复”，但“空”也可能是正常重建，不能单独作为恢复依据。
  - 方案“只补缺失、不覆盖现有”无法区分“更新后丢失”与“用户主动删除/禁用”。用户更新后决定不要 wallpaper engine，guard 会把它加回来；用户更新后新装一个插件，guard 可能把它当作“多余”忽略，或在写 bundles 顺序时打乱。
  - 方案没有规定“什么证据下才自动还原”。只靠版本变化 + 缺项，会把任何更新后的手工整理都当成事故。
- **为什么重要**：
  - 这是最容易造成“用户觉得工具在跟我对着干”的地方。恢复过度会覆盖用户意图，恢复不足会漏掉官方可选功能。
  - 如果 `.bak` 已经存在，说明恢复流程确实执行过；如果没有 `.bak`、bundles 也不是基线，可能只是用户手动改配置，不能直接还原。
- **建议补充**：
  1. 把 bundle 分三类：`安装包基线`（base/web-app 等当前版本的 template）、`官方可选`（official bundles 列表，如 agent-team）、`第三方`。还原目标是“快照中的非当前基线集合”，不是“第三方集合”。
  2. 建立“恢复证据”判定：存在 `cordis.patch.yml.bak-*`（时间戳在本次更新前后）或 bundles 被重置为当前 `WEB_PROFILE.bundles` 或 `operations.jsonl` 有相应记录；只有证据充分才自动还原，否则只提示 + 让用户确认。
  3. 定义“缺失”与“用户删除”的区分：如果当前 dependencies 中仍有该包、只是 bundles 里没有，且没有恢复证据，视为“用户禁用”；如果依赖和包都不在，视为“未安装”，不要自动加回。可选：读取 `.dsh-market/state.json`、`operations.jsonl` 的最近操作时间辅助判断。
  4. patch 恢复优先级：如果存在 `.bak-*` 且比快照新，优先用 `.bak`；否则用快照；当前文件非空且与两者都不同，输出 diff 让用户选，默认保留当前。不要因为“文件为空”就静默覆盖。
  5. 在报告里列出“已还原 / 已跳过（用户改动）/ 冲突待处理”三类，而不是只写“恢复完成”。
- **涉及方案章节**：3.4、5.4、7.3、第六节

#### P0-6 包级还原用 `file:<tgz>` 会改写依赖规格，离线/回滚路径不成立

- **问题**：
  - 方案 3.4.3 把“本地归档”放在第一位：`dsh plugin --profile desktop add file:<snapshot>\packages\<pkg>@<ver>.tgz`。pnpm 安装本地 tarball 时会把 `package.json` 依赖写成 `file:` 路径，而不是原来的 registry 版本/范围；快照目录一旦被保留策略删除，这个依赖就永久指向不存在的文件。
  - 一个顶层 tgz 不包含 wallpaper-engine 的 8 个子包（`-about-notice`、`-fonts`、`-fx`、`-glass`、`-mascot-avatar`、`-media-bridge`、`-parallax`、`-pet-link`）；只装顶层 tgz 不能恢复完整依赖闭包。
  - `pnpm pack` 可能触发 `prepack`/`prepare`（例如 `dshmarket` 有 `prepack: node scripts/preflight.mjs`），而安装后的包通常没有 devDependencies，pack 可能失败；方案把 `pnpm pack` 当作 P2 的简单实现，低估了这一点。
  - 方案把 `pnpm install --offline` 排在第二位。实际上，如果 `package.json` 和 `pnpm-lock.yaml` 都在、只是 `node_modules` 丢失，`pnpm install --offline --frozen-lockfile` 才是最短、最可复现的恢复路径；应该优先于 `file:tgz`。
  - “首启失败自动回滚”没有定义失败判据；如果 App 启动失败但没写 crash 日志，或只是插件静默不加载，guard 不会知道。
- **为什么重要**：
  - 包级还原是“兜底”，一旦用错方式，会把 profile 的依赖规格改坏，后续 DSH 更新/插件管理器升级都会受影响。
  - 离线场景是用户明确关心的（策略 A 需要联网；断网时要有可用路径）。当前顺序会先引入一个更差的 `file:` 状态。
- **建议补充**：
  1. 包级恢复顺序改为：**恢复 package.json + pnpm-lock.yaml → `dsh.cmd plugin --profile desktop install --offline --frozen-lockfile`**；离线失败且用户同意后再联网；`file:tgz` 只作为最后手段，且安装后要把依赖规格改回原 registry spec，并重新生成 lock（或恢复原 lock 后 `pnpm install --lockfile-only`）。
  2. 归档要按 lockfile 生成完整闭包（至少顶层依赖的所有传递依赖），而不是只 pack 顶层包；用 `pnpm list --depth Infinity --json` 或 lockfile 的 `packages` 段枚举。
  3. 记录原始 dependency spec（`^0.4.2` 或 `1.4.2`）与精确版本，回滚时恢复 spec 而不是写死 `file:`。
  4. 定义“首启失败”的可观测判据：新版本启动后 host 未 ready、出现新 `crash-*.log`、进程在 N 秒内退出、或 guard 的只读 check 仍发现 bundles 缺失；不要只依赖 crash 文件。
  5. 测试用例必须覆盖“删掉 node_modules、清空 pnpm store、断网”三种情况，并确认最终 `package.json` 没有 `file:` 残留。
- **涉及方案章节**：3.1、3.3（离线）、3.4.3、3.4.5

#### P0-7 策略 A 只有目标，没有可执行的选择算法与失败边界

- **问题**：
  - 方案 3.3/7.3 说“查 registry 的 `latest`/可用版本 → 用官方 evaluator 预检 → 兼容则安装”。但没有定义：
    - 用**当前 runtime** 还是**更新后的目标 runtime** 做预检？更新后 guard 运行在新版本下，`getDshRuntimeVersion()` 是新的，看似可以；但若要在下载期间预下载，就必须把目标版本传给 evaluator 的第三个参数。
    - 候选版本如何排序：`latest`、所有 versions、dist-tags、prerelease、deprecated、`dsh.bundle` 缺失的版本、platform 不支持的版本。
    - 选择“最高兼容版本”还是“最低满足版本”？跨 major 是否允许自动升级？插件数据格式变化怎么办？
    - registry 不可达、私有源、npmmirror、认证、超时、离线时怎么办？
    - 安装失败/装到一半崩溃/安装后 DSH 仍不兼容时怎么办？
    - 安装要加 `--save-exact` 吗？升级后 `package.json` 的 spec 是 `^` 还是精确版本？
    - 升级到新版本后插件自身数据是否需要迁移？用户已明确“暂不备份插件数据”，但方案没有据此限制 major 自动升级。
  - 方案说“升级后更新 bundles/deps”，但 `dsh plugin add` 内部已经会 `reconcile` 并把新 bundle 追加到 `dsh.profile.bundles`；guard 再写一次可能打乱顺序或重复。方案没有定义“以 CLI 的结果为准”还是“以后再覆盖”。
  - 方案没有审计记录字段（选了哪个版本、为什么、来自哪个 registry、integrity、被拒绝的候选及原因），出问题时无法解释。
- **为什么重要**：
  - 策略 A 是用户已确认的默认动作。规格不写清，实现者只能凭感觉做选择；一旦自动升到不兼容/有数据迁移的版本，用户会失去可解释性和回滚能力。
  - “自动升级”如果没有明确的失败边界，很容易变成“自动改坏”。
- **建议补充**：
  1. 写一段伪代码/决策表：
     - 输入：包名、已安装版本、原始 spec、目标 DSH runtime 版本、registry 配置、是否允许 prerelease/major。
     - 候选：`semver.gt(v, installed)`；排除 deprecated（除非无其他候选）；必须有 `dsh.bundle`（如果是 bundle 插件）；`dsh.bundle.platforms` 包含 win32；用官方 evaluator 对**目标 runtime** 预检；按稳定版优先、版本号降序、同版本按 registry 顺序。
     - 上限：最多查 N 个版本（例如 20），每个 lookup 有超时/取消；失败后不无限重试。
     - 结果：命中则 `dsh.cmd plugin --profile desktop add <pkg>@<ver> --save-exact`；未命中则报告“无兼容版本”，绝不自动豁免。
  2. 明确 major 升级默认需要用户确认（或至少黄色提示 + 报告），因为可能涉及插件数据格式；用户拒绝时保留旧版/禁用/豁免三选一。
  3. 明确 `dsh plugin add` 之后以 CLI 写回的 `package.json`/bundles 为准，guard 只做校验和报告，不重复写；如果需要调整顺序，单独一步并记录 diff。
  4. 审计记录：候选列表、拒绝原因、选中的 registry/integrity、命令、退出码、安装前后版本、耗时；写入 `report.json` 和 `state.json`。
  5. 明确 registry 不可达/离线/私有源的降级路径；不要在没有用户同意时回退到公网 registry。
- **涉及方案章节**：3.3、3.4、第六节、7.3

### P1 重要（会影响可用性/可维护性，建议实现前补齐）

#### P1-1 版本来源与“appVersion vs dshVersion”混用

- **问题**：方案 3.2 读 `resources\runtime\runtime.json`（路径不存在；实际在 `primary-runtime\runtime.json`），并把 `desktopVersion` 与快照的 `dshVersion` 比较。`desktopVersion` 是桌面应用版本，`dshVersion` 是运行时版本；当前两者恰好都是 0.2.2-rc.1，掩盖了字段混用。纯 UI 更新（app 变、dsh 不变）会误触发插件检查/还原；dsh 变但 app 不变时会漏检。
- **为什么重要**：误触发会做无谓的写操作和重启提示；漏检会让插件继续被禁用。
- **建议补充**：在 `snapshot.json`/`state.json` 同时存 `appVersion` 和 `dshVersion`；app 版本从 `primary-runtime/runtime.json` 的 `desktopVersion` 或 `app.asar/package.json` 读，dsh 版本从 `app.asar/dsh/package.json` 或官方 `getDshRuntimeVersion()` 读；比较时同名字段比较。新增“仅 app 变化”的用例。
- **涉及章节**：3.1、3.2、3.3

#### P1-2 仅凭 `crash-*.log` 判断“走了禁用插件恢复”会误报

- **问题**：`main.js` 的 `reportFatal` 在 `shuttingDown` 为 true 时也会写 crash 报告，只是不弹恢复框；现有 11-07 的 `crash-...-host.log` 内容是 `host exited with 1073807364`，更像 host 退出而不是插件兼容崩溃。方案 3.2 把“发现新 crash 日志”与 `.bak` 并列作为恢复证据。
- **为什么重要**：误报会让 guard 在正常退出后提示“插件被禁用”，甚至触发不必要的还原；也可能掩盖真正的崩溃。
- **建议补充**：恢复证据分级：`.bak-*`（强）> bundles 被重置为当前基线（强）> 新 crash 日志且 `phase/error` 匹配 host 启动失败（中）> 用户手动报告（弱）。只有强证据才自动还原；中证据先只读 check + 提示；不要解析/复制 crash 文件全文（可能含用户内容）。
- **涉及章节**：3.2、5.3

#### P1-3 client 端兼容性只做 manifest 判定会漏，且方案没有可执行的静态检查

- **问题**：`dsh-whale-widget@0.4.2` 没有 `engines`/`peerDependencies`，evaluator 对 0.3.0 也返回“兼容”；但它的 `dsh.client.inject` 依赖内置 client 包。`dsh-plugin-wallpaper-engine`/`dshmarket` 也有 `dsh.client.inject`。方案风险 1 承认“client 兼容性无法只靠 manifest 判定”，但只给了“首启崩溃自动回滚”，没有静态检查，也没有“未验证”状态。
- **为什么重要**：最可能出现的真实场景是“manifest 全绿但 UI 白屏/功能失效”，guard 报告“已恢复”，用户却用不了。
- **建议补充**：增加静态预检：`dsh.client.inject` 的每个包名在目标 runtime 中可解析；`dsh.bundle.patch` 存在且可解析；patch 插入的 entry name 可解析（过滤 `cordis:*`/相对路径）；`dsh.bundle.platforms` 包含 win32。无法确认的项标记 `unverified`，不要自动升级/自动宣告成功。首启后做健康检查：host 进程存活 N 秒、无新 crash、如可获取本地 Web URL 则探测 HTTP 200；仍无法验证的，报告“需人工确认 UI”。
- **涉及章节**：3.3、5.1、5.3

#### P1-4 复用官方 evaluator 的路径/导出变化没有降级方案

- **问题**：方案把 `file:///D:/DeepSeek/resources/app.asar/dsh/node_modules/@deepseek-ai/dsh-app-boot/lib/index.js` 写死，并假设 `getDshRuntimeVersion`/`evaluatePluginCompatibility` 永远存在。DSH 更新可能改包路径、导出名、打包方式，甚至不再把源码放进 asar；Electron 版本变化也可能影响 `--expose-internals`/ESM 加载。
- **为什么重要**：guard 的核心判定依赖这个导入；一旦失败，工具会在最需要它的时候“检查不了”，而方案没有“unknown”与“兼容”的区分。
- **建议补充**：helper 先探测官方模块（路径候选、导出存在性、版本）；成功则用官方结果，失败则用**自包含 fallback evaluator**（vendored semver + 与官方一致的 `engines.dsh`/peer 规则），并记录 `engine: official|fallback`；fallback 结果与官方结果做语料对拍（至少覆盖当前三个插件、prerelease、workspace、缺失字段、非法 range）。任何导入/解析错误都归类为 `unknown`，绝不当作“兼容”。fallback 需要单元测试，不能靠手工。
- **涉及章节**：3.3、3.5、5.1

#### P1-5 兼容规则边界没有写全

- **问题**：方案写了“有 `engines.dsh` 只用它；否则看 `@deepseek-ai/dsh*` peer”，但没有写：optional peer 仍会被 evaluator 检查（`peerDependenciesMeta` 不豁免）；`@deepseek-ai/cordis`/`@deepseek-ai/schemastery`/`react` 等 peer 被忽略；`includePrerelease: true`；`workspace:^/~/*` 在 engines.dsh 中视为不满足、在 peer 中视为当前 runtime；manifest 字段非法时 evaluator 抛错；`dsh.bundle.platforms` 的平台检查是单独的。
- **为什么重要**：实现者容易写出“看起来一样、边界不同”的判定，导致和 DSH 启动行为不一致；尤其是 optional peer 和 nightly prerelease。
- **建议补充**：在方案中列出判定表与反例；把 evaluator 的异常映射为 `unknown`；加一组 fixture 测试（合法/非法 engines、optional peer、workspace、prerelease、空 range、缺 name/version）。
- **涉及章节**：3.3

#### P1-6 精确豁免的生命周期与“崩溃循环”没有处理

- **问题**：`compatibility.json` 的豁免绑定“精确包版本 + 精确 DSH 版本”；`setProfileVersionExemption` 只允许对当前 runtime 授权，且必须 `acceptRisk`；文件损坏时 `readProfileCompatibility` 返回 `rewritable: false`，不能直接改写。方案说“旧版本豁免自动失效并提示”，但没写：如何清理、如何避免重复提示、用户坚持豁免后插件反复崩溃怎么办、guard 是否会自动恢复一个“已豁免但会崩”的插件。
- **为什么重要**：豁免是用户明确承担风险的路径；如果 guard 在每次启动都恢复它，会造成“崩溃→恢复→再崩溃”的循环，甚至数据损坏。
- **建议补充**：豁免只用 `dsh.cmd plugin allow-version`/`revoke-version` 写，不直接改 JSON；保留 `rewritable: false` 的文件并提示用户手工修复；每次启动最多提示一次；连续 N 次（如 2 次）首启失败或崩溃则进入“隔离”状态（不自动恢复该插件，只保留报告），由用户决定。旧版本豁免不删除，但标记 inactive，提供“清理旧豁免”按钮。
- **涉及章节**：3.3、3.4、5.1

#### P1-7 registry 查询/私有源/离线/版本选择的实现细节缺失

- **问题**：方案只说“查 registry”。实际 DSH 插件管理器用 `pnpm view` 在 profile 目录执行，读取 profile 的 `.npmrc`/workspace 配置，按 registry plan 依次尝试（私有源优先，npmmirror fallback），有超时、失败分类和 `versionListLimit`。guard 如果自己发 HTTP，容易绕过代理/认证/私有源，或把私有包名发到公网。
- **为什么重要**：用户可能配置私有 registry 或镜像；错误的查询会泄露包名、拿不到正确版本，或在离线时长时间卡住。
- **建议补充**：复用“在 profile 目录运行 bundled pnpm view”的方式；读取 `.npmrc`/环境变量；显式 `--registry` 只使用配置中的源；设置超时/取消；解析 `dist-tags`/`versions`，过滤 deprecated、缺 `dsh.bundle`、平台不符；限制候选数量；记录查询失败类型（network/auth/not-found）；日志脱敏。离线时直接报告“无法查询”，不要无限重试。
- **涉及章节**：3.3、3.4、7.3

#### P1-8 升级失败/装到一半崩溃的恢复细节不足

- **问题**：`runProfilePnpm` 会在失败时恢复 `package.json`/`pnpm-lock.yaml`，但 `node_modules` 可能已被 pnpm 改了一半；`.plugin-manager\run.json` 可能留下孤儿 pnpm 进程记录；方案没有定义 guard 自己的超时、杀进程树、重试、磁盘空间检查和“装到一半”的状态恢复。
- **为什么重要**：升级失败是常态（网络、registry、构建脚本、权限）。处理不好会留下“package.json 已改、node_modules 半新半旧”的 profile，DSH 下次启动可能直接失败。
- **建议补充**：升级前检查磁盘空间（pnpm store + temp）；设置总超时和“无输出超时”；超时后终止进程树并清理 `run.json`（或按 DSH 规则等待/删除）；升级失败后跑一次 `pnpm install --offline --frozen-lockfile` 修复，再校验；把失败阶段写入 state，下一次启动先修复再继续；记录 pnpm 日志路径。
- **涉及章节**：3.3、3.4.3、3.4.5

#### P1-9 还原合并/冲突/回滚的规则不完整

- **问题**：方案有“只补缺失、不覆盖现有”“patch 冲突给 diff”“回滚 restore-backup”，但没有定义：
  - bundles 的顺序如何合并（新的内置 bundle 插在哪、第三方原有顺序如何保持）；
  - dependencies 的 spec 冲突（快照 `^0.4.2` vs 当前 `0.5.0`）以谁为准；
  - pnpm-lock 与 package.json 不一致时先修哪个；
  - `.dsh-market/state.json` 是否恢复；
  - 回滚是回滚“本次还原”还是“回到某个快照”；
  - 幂等性（重复执行 restore 不应重复插入）；
  - 首启失败自动回滚如何避免把用户自己的崩溃误判。
- **为什么重要**：没有合并规则，实现者每次遇到冲突都可能做不同决定；用户看到的结果不可预测。
- **建议补充**：写一张“字段/来源/冲突优先级/是否自动/报告内容”的表；所有写操作幂等（按 key 去重、按原顺序插入）；restore-backup 带 operationId；回滚只回滚该 operation；首启失败判定与用户手动崩溃分开（见 P1-2/P0-6）。
- **涉及章节**：3.4、3.4.5

#### P1-10 App 运行检测与安全退出没有实现方案

- **问题**：方案说“检测到 App 正在运行且需要 pnpm 时，等待退出或提示用户”，但没有定义怎么检测、怎么区分“窗口关了但还在托盘”、怎么保证完全退出、用户不退出怎么办。本机 `Get-Process` 能看到 3 个 `DeepSeek Harness` 进程，关闭窗口后进程仍在。
- **为什么重要**：误判“已退出”会在 host 仍运行时装包；误判“还在运行”会让用户永远等不到升级。
- **建议补充**：用 `Get-Process` 的 `ProcessName` + `Path`（按安装目录过滤）检测所有相关进程；要求连续 2～3 秒无进程才算退出；不自动 kill；提供“请从托盘退出 DSH”的明确引导 + “我已退出，继续”按钮；高级“强制结束”二次确认并提示会话风险；安装前再检查一次，启动中则中止并回滚。
- **涉及章节**：3.6、7.3

#### P1-11 `state.json`/`config.json` 的 schema、原子性与迁移未定义

- **问题**：方案只列了 `state.json` 的几个字段，没有 schemaVersion、默认值、损坏处理、原子写、迁移；`config.json` 也只有一行描述。guard 崩溃/升级后可能读到半截 JSON 或旧字段。
- **为什么重要**：状态文件是跨进程、跨重启的；损坏会导致工具无法启动或重复操作。
- **建议补充**：为 `config.json`/`state.json` 定义 `schemaVersion`、字段、默认值、校验与迁移；原子写（临时文件 + rename）；损坏时备份并重建；操作 journal（见 P0-4）；`state.json` 不存敏感信息。
- **涉及章节**：3.1、3.5、7.1

#### P1-12 备份保留/磁盘/位置的规则互相矛盾

- **问题**：方案 3.1 说“最近 5 份 + 每个应用版本至少 1 份，总量上限 ~300 MB”。这三个条件可能冲突（版本多时“每个版本 1 份”会超 300 MB）；没有定义淘汰顺序、是否保留 pre-update、磁盘不足时怎么办。备份路径硬编码 `%USERPROFILE%\.dsh`，没有跟随 `DSH_HOME`。`guard.log`/`report-*.md` 没有轮转/保留。
- **为什么重要**：用户可能长期使用，快照无限增长；磁盘满会导致快照/还原半途失败。
- **建议补充**：定义配额算法（先保 pre-update + 最近 N 份，再按版本保留，超限从最旧删）；每次快照前检查磁盘，空间不足则跳过 `--full` 包归档并警告；备份根目录跟随 `DSH_HOME`（可配置）；日志按大小/份数轮转，报告按数量/天数保留；给出占用统计。
- **涉及章节**：3.1、3.5、7.1

#### P1-13 工具自身健壮性清单缺失

- **问题**：方案没有覆盖：单实例（托盘 + CLI 同时跑）、开机自启的命令行引号/控制台闪窗、PowerShell 5.1 下 UTF-8 BOM/中文路径、杀毒软件误报、DSH 被卸载/换安装路径、工具自身升级、执行策略/权限。
- **为什么重要**：这些不是边缘情况，而是绿色 PowerShell 工具的日常故障来源；任何一个都可能让用户觉得“工具坏了”。
- **建议补充**：
  - 单实例：命名 mutex；托盘已运行时 CLI 通过 IPC/临时文件让托盘执行，或明确只读模式。
  - 自启：HKCU Run 命令全路径加引号；避免 `-WindowStyle Hidden` 仍闪 console（可用 VBS/`wscript` 或编译壳）；移动文件夹后自检并修复；卸载时删除 Run 值。
  - PS 5.1：脚本存为 UTF-8 with BOM；避免 `??`、三元、`ConvertFrom-Json -Depth` 等高版本语法；中文路径用 `-LiteralPath`；控制台编码显式设置。
  - DSH 卸载/移动：检测安装目录不存在时进入 `disabled` 状态，不弹错误循环；提供“重新定位”。
  - 工具自身升级：版本号、配置迁移、备份兼容；不要覆盖用户 `config.json`。
- **涉及章节**：7.1、7.2、3.6

#### P1-14 通知/首次引导/失败入口/托盘状态/多 profile 不完整

- **问题**：方案说“Windows Toast”，但未打包的 PowerShell 应用没有 AppUserModelID/开始菜单快捷方式，Toast 往往不显示；设计稿又要求 Toast 样式。没有首次运行引导（范围说明、权限、autostart、首次快照）、失败时的人工入口、托盘状态机、多 profile（web/desktop）说明。
- **为什么重要**：用户第一次运行不知道它在做什么；失败时只看到托盘变色但不知道怎么处理；Toast 不显示会让“已备份/待处理”完全无感。
- **建议补充**：首版优先用 `NotifyIcon.ShowBalloonTip`（可靠）或创建带 AUMID 的快捷方式后再用 Toast；定义托盘状态（正常/待处理/升级中/失败/DSH 未找到）及图标/提示；首次运行向导；失败面板提供“打开报告/重试/回滚/退出 DSH 并继续/打开插件管理器”；明确只守护 `desktop` profile，web profile 忽略并说明。
- **涉及章节**：3.3、7.2、7.5、设计说明第三节

#### P1-15 交付形态与设计稿不匹配，工作量被低估

- **问题**：设计定稿要求深/浅双主题、1840×1080 的托盘弹层（状态卡、主按钮、最近活动、设置窗口、兼容性提示卡），并注明“可直接映射到 WPF / WebView2”；方案 7.1 的交付物只有 `guard.ps1` + `icon.ico`，7.6 才说“可选 PS2EXE/.NET 单文件”。PowerShell `NotifyIcon` 的默认菜单/气泡做不出设计稿的卡片式弹层；用 PowerShell 承载 WPF XAML 可行，但工作量、调试成本和 DPI/主题适配都不低。
- **为什么重要**：这不是“美化”问题，而是交付范围不一致：按设计稿验收，PS1 简单托盘一定不通过；按 PS1 实现，设计稿的大量内容没有落点。
- **建议补充**：二选一并写进方案：
  - **A（推荐首版）**：WinForms/WPF 小工具（.NET 8 单文件自包含或 framework-dependent），托盘 + 简洁设置窗；设计稿作为视觉参考，不承诺 1:1；代码签名/杀软兼容单独排期。
  - **B（保持 PS1）**：明确 UI 只做托盘菜单 + 一个简单 WinForms 设置对话框，删掉/降级设计稿中的富面板，避免验收争议。
  - 无论哪种，3～4 天都不够；按 1.4 重新排期。
- **涉及章节**：4、7.1、7.6、设计说明第三节

#### P1-16 安全/隐私边界不足

- **问题**：方案说“报告与日志不落盘敏感信息”，但没有具体机制：`cordis.patch.yml` 可能含用户配置/密钥；pnpm 子进程会继承 guard 的环境变量（可能含 API Key/Token）；pnpm 输出可能含 registry URL/token；crash 日志可能含用户内容；备份目录 ACL 未定义；供应链只依赖 pnpm integrity，没有记录/校验来源。
- **为什么重要**：桌面工具长期驻留，一次日志泄露就可能暴露凭据；备份目录被同步/分享也会泄露配置。
- **建议补充**：备份目录显式 ACL（仅当前用户）；报告只写路径/哈希，不写 patch 内容；调用 pnpm 前过滤 `*KEY*/*SECRET*/*TOKEN*/*PASSWORD*` 等环境变量（参考 DSH 的 `scrubbedParentEnv`）；日志正则脱敏 `_authToken`、`Authorization`、URL query；记录 registry/integrity/tarball URL，安装后校验 lock 的 integrity；不读取 `.credentials.yaml`/DPAPI；提供“导出报告前预览/脱敏”。
- **涉及章节**：3.6、7.3、7.5

#### P1-17 可测试性/可观测性没有设计

- **问题**：方案没有测试策略、fixture、mock registry、`--json`/`--dry-run`、退出码约定、日志级别；PowerShell 逻辑与 UI/文件系统耦合，难以单元测试。
- **为什么重要**：这类工具的正确性依赖大量边界（锁、版本、离线、崩溃、恢复），没有自动化测试就只能靠真实更新碰运气；而真实更新不可频繁复现。
- **建议补充**：纯函数与 I/O 分层；Pester 单测覆盖版本选择/合并/保留/证据判定；集成测试用临时 `DSH_HOME` + 假安装目录 + 本地 mock registry；`--json` 输出、`--dry-run`、明确退出码（0 成功/1 失败/2 待人工/3 未找到）；日志级别与操作 ID；CI 可跑的非破坏性用例。
- **涉及章节**：4、7.4

## 三、建议补充的验收用例清单

### 3.1 测试环境与原则

- 所有破坏性用例在 `%TEMP%\loom-verify\` 下的 **DSH_HOME 副本 + 假安装目录**上执行，通过 `--dsh-home`/`--install-dir` 注入；不要直接改真实 profile。
- 安装目录用“假安装目录”提供 `resources\runtime\primary-runtime\runtime.json`、`resources\runtime\cli\bin\dsh.cmd` 的 stub，或复制一份只读 app.asar 路径；真实 app.asar 只读使用。
- registry 用本地 mock（静态 JSON + tarball，或 Verdaccio）；需要验证私有源/离线时切换 `--registry` 与断网。
- 真实 nightly 更新只在虚拟机快照上验证，不在日常机器上反复执行。
- 每个用例都检查：不写安装目录、不改 app.asar、不改真实 profile；失败可回滚；报告/日志无密钥。

## 四、对交付形态 / 命名 / 设计一致性的一句话评价

**“绿色托盘 + 同名 CLI、不做 DSH 插件”的交付形态与 Loom 的织机隐喻是自洽且有说服力的；但方案正文仍用 `dsh-guard`、设计稿的富面板与 PS1 托盘实现明显不匹配，且 `loom` 作为通用命令名存在冲突风险——建议先统一命名为 `Loom`/`loom-dsh`，并把首版 UI 收敛到 WinForms/WPF 能交付的形态，再谈“按设计稿验收”。**

## 五、方案中写得最好、不用改的部分

1. **第一节的三条机制诊断**：兼容性拦截、崩溃恢复“禁用第三方插件”、安装期版本拒绝，区分清楚，且有 `evaluatePluginCompatibility`/`loadProfileDirectory`/`prepareProfileEntries`/`sanitizeProfile` 的源码依据。这是整个方案最有价值的部分，不需要重做。
2. **“不做 DSH 插件”的三条硬理由**：会被恢复流程连坐、宿主运行中不能安全重装包、进程外监控能力，论证成立，交付形态选择正确。
3. **边界纪律**：只操作 `profiles/desktop`、不碰安装目录/app.asar、写前备份、可回滚、风险豁免永不静默——这些原则都对，应保留为实现的硬约束。
4. **复用官方 evaluator 的方向**：不自创兼容规则，而是尽量与 DSH 启动行为一致；这是降低长期维护成本的关键判断。
5. **7.5 的“交互的度”**：全兼容不打扰、失败才出现、不弹模态、报告落盘——产品分寸感很好，建议在实现中坚持。
