### 0.2 术语
| 术语 | 含义 |
|---|---|
| **installDir** | DSH 桌面版安装目录（本机 `D:\DeepSeek`），由安装定位器解析，不硬编码 |
| **DSH_HOME** | DSH 用户数据根（默认 `~/.dsh`，可由环境变量覆盖） |
| **profile** | `%DSH_HOME%\profiles\desktop`；插件清单 `package.json`、`cordis.patch.yml`、`node_modules`、`compatibility.json` 都在这里 |
| **bundle** | `dsh.profile.bundles` 里的一个包（含 `dsh.bundle` 声明）；分安装包基线 / 官方可选 / 第三方三类 |
| **appVersion** | 桌面应用版本（`primary-runtime\runtime.json` 的 `desktopVersion`，或 `app.asar/package.json`） |
| **dshVersion** | DSH 运行时版本（官方 `getDshRuntimeVersion()`，当前 0.2.2-rc.1） |
| **evaluator** | DSH 官方兼容判定 `evaluatePluginCompatibility(manifest, exemptions, runtimeVersion)` |
| **策略 A** | 用户默认选择：自动查询并升级到与目标 dshVersion 兼容的插件版本 |
| **上次好快照** | 最近一次在版本变化前采集、且校验通过的快照；更新处理完成前禁止被覆盖 |
| **三次启动** | 更新自动拉起的新版本（第 1 次）→ 用户完全退出 → guard 升级/还原 → guard/用户再次启动（第 3 次） |

## 1. 背景与诊断结论

### 1.1 为什么“更新后插件像没装一样”
| # | 机制 | 依据 | 现象 |
|---|---|---|---|
| A | **兼容性拦截**：DSH 启动装载 profile 时，对每个 bundle / 插件行按 manifest 的 `engines.dsh`（无则看 `@deepseek-ai/dsh*` peerDependencies）做 semver 检查，不满足则禁用该行 / 跳过该 bundle | `@deepseek-ai/dsh-app-boot`：`evaluatePluginCompatibility`、`loadProfileDirectory`、`prepareProfileEntries` | 更新跨版本后旧插件“消失/失效” |
| B | **崩溃恢复“禁用第三方插件”**：host 致命错误时弹恢复框，选择该项会备份 `cordis.patch.yml` 为 `.bak-<时间戳>`，把 bundles 重置为 `WEB_PROFILE.bundles`（仅 base + web-app），保留包、重启 | 桌面端 `main.js`：`DesktopFatalRecovery` → `DesktopProjectManager.disableAllPlugins` → `sanitizeProfile(..., WEB_PROFILE.bundles)` | UI 显示“未安装”，必须重新添加；**agent-team 等官方可选 bundle 也会被拿掉** |
| C | **安装期版本拒绝**：插件管理器/`dsh plugin add` 会预检兼容性，不兼容直接拒绝；可用精确版本豁免承担风险 | `@deepseek-ai/dsh-plugin-manager`、`compatibility.json` | “重装”实际多是升到兼容版本 |

### 1.2 本机事故痕迹（不等同于结论）
- profile 创建于 2026-10-17，11-04 应用更新后仍存在 → **更新本身不删 profile**；插件与配置位于安装目录之外。
- `%APPDATA%\@deepseek-ai\dsh-desktop\logs\crash-2026-11-07T16-09-50-689Z-host.log`：host 退出异常（非插件报错文本），关机时也可能写同类报告 → **crash 文件只能作为弱/中证据**。
- `plugin-operations\operations.jsonl`：11-07 启用过 agent-team，11-14 重装过三个插件 → 与“更新/恢复后重装”经历吻合。

### 1.3 结论
方向成立：**快照保险 + 官方兼容判定 + 文件级还原 + 策略 A 升级 + 兼容提示**；但不能按 v1 的简单时序与命令假设实现，必须按 v2 的状态机、锁与证据规则落地。

## 3. 关键事实修正（v1 假设 → 实测）

| # | v1 假设 | 实测/源码事实 | v2 处理 |
|---|---|---|---|
| 1 | 读 `resources\runtime\runtime.json` | 实际为 `resources\runtime\primary-runtime\runtime.json`（`desktopVersion`） | 安装定位器按候选路径解析；appVersion/dshVersion 分开记录与比较（6.1、P1-1） |
| 2 | 直接执行 `dsh plugin --profile desktop ...` | PATH 无 dsh；普通 CLI 有 `rejectElectronProfile` 会拒绝 desktop | 只用 installDir 下 `resources\runtime\cli\bin\dsh.cmd`，见 6.2 |
| 3 | `pending\` 出现安装包 = 最佳快照点 | 下载期先写 `pending\temp-*.exe`，完成后 rename 并写 `update-info.json`；随后应用内立即进入安装确认；本机残留 11-07 的 293MB 旧包 | 触发改为 `temp-*` 出现/下载开始；按 `update-info.json` 的 sha512 + 版本去重；见 8.2 |
| 4 | 更新后 App 会退出，可等退出后升级 | `quitAndInstall(true,true)` → NSIS `--updated --force-run`，装完立即拉起新版本，无稳定空窗 | 明确三次启动；包级升级需用户再退出一次；见 8.1 |
| 5 | 恢复基线 = 内置 base/web-app，只还原第三方 | 恢复会重置为 `WEB_PROFILE.bundles`（base + web-app），agent-team 也会丢 | bundle 分三类；还原“快照中的非当前基线集合”；见 12.1 |
| 6 | 只有 `package.json` 文件锁 | 三套机制：`profile\lock`（PID）、`package.json.lock`（120s）、`.plugin-manager\run.json`（孤儿 pnpm 记录） | 锁矩阵 + 读一致性协议 + journal；见 7 |
| 7 | 包级兜底用 `file:<tgz>` | pnpm 会把依赖写成 `file:`；顶层 tgz 不含 wallpaper 8 个子包；`pnpm pack` 可能触发 prepack | 顺序改为恢复 package.json+lock → `install --offline --frozen-lockfile`；见 12.5 |
| 8 | helper 用系统 Node 跑 evaluator | 系统 Node 无法 import app.asar；`runtime\bin\node.cmd` 依赖未设置的 `DSH_DESKTOP_NODE_EXECUTABLE` | helper 必须 Electron Node 模式；见 6.3 |
| 9 | manifest 能覆盖全部兼容性 | `dsh-whale-widget` 无 engines/peers → 恒判兼容，但存在 `dsh.client.inject` | static precheck + unverified + 首启健康检查；见 10.3/10.6 |
| 10 | 新 crash 日志 = 走了恢复流程 | 关机也会写 crash 报告；11-07 日志更像 host 退出 | 证据分级：`.bak-*`/基线重置（强）> crash 匹配（中）> 用户报告（弱）；见 12.2 |
| 11 | 策略 A 有目标即可 | 缺当前/目标 runtime、候选排序、prerelease、私服、离线、`--save-exact`、回滚、审计 | 决策表 + 审计 + 失败边界；见 11 |
| 12 | PS1 + `icon.ico` 能承载设计稿 UI | NotifyIcon 做不出卡片式弹层/设置窗/双主题 | UI 选型定为 **.NET 10 WPF（自包含单文件 exe）**，见 13.1 |

## 4. 目标与范围

### 4.1 目标
1. **更新前**可靠留存“最后一份好状态”（清单/精确版本/来源/配置/兼容豁免/离线包）。
2. **更新后**自动检测版本变化；能文件级修复的立即修复（只需重启生效）；必须装包的在 App 完全退出后执行。
3. **兼容性**：与 DSH 启动判定一致；区分 compatible / incompatible / unverified / unknown；不把“未知”当“兼容”。
4. **策略 A**：按决策表自动升级到兼容版本；无兼容版本只提示，绝不自动豁免风险。
5. 全过程可审计、可回滚、不打断用户；失败给出明确人工入口。

### 4.2 明确不做
- 不修改安装目录、不修改 `app.asar`、不写入 DSH 安装文件。
- 不自动 kill DSH 进程；不静默自动接受风险豁免；不自动做 major 升级（需确认）。
- 不备份插件业务数据（用户决定；major 风险见 11.4）；不处理 web 等其它 profile。
- 不依赖系统 pnpm / 系统 Node / 联网完成核心恢复（联网仅用于查询/升级与缺失包）。

### 4.3 硬约束（实现纪律）
只操作 desktop profile；所有写操作先备份并可回滚；不把未知状态当兼容；报告/日志不落敏感信息；单实例、无管理员权限运行。

## 5. 总体架构与数据布局

### 5.1 组件
```
┌───────────────────────────── Loom（单进程，绿色） ─────────────────────────────┐
│  TrayApp/CLI（.NET 10 WPF，loom-dsh.exe <command>）                              │
│      │ 单实例 mutex / 命令队列                                                    │
│  ┌───┴───────────────────────────────────────────────────────────────────────┐  │
│  │ Core                                                                      │  │
│  │  InstallerLocator   DshCli       Evaluator(official|fallback)             │  │
│  │  AppWatcher         Snapshot     Restorer         UpgradePlanner           │  │
│  │  RegistryClient     LockManager  StateStore+Journal  Notifier/Reporter    │  │
│  └───────────────────────────────────────────────────────────────────────────┘  │
└───────────────┬───────────────────────────────┬────────────────────────────────┘
                │ 读取/写入（加锁、备份）          │ 调用
                ▼                               ▼
   %DSH_HOME%\profiles\desktop        installDir\resources\runtime\cli\bin\dsh.cmd
   %LOCALAPPDATA%\Loom\（工具数据）      + Electron Node helper（读 app.asar 官方模块）
```

### 5.2 数据布局（工具数据与 DSH 数据分离）
```
%LOCALAPPDATA%\Loom\                     ← 工具根（不放进 DSH_HOME，避免被重置连带）
  config.json                            ← 设置（schemaVersion）
  state.json                             ← 状态（schemaVersion、lastSnapshot、pendingUpdate、journal 指针）
  journal\<operationId>.jsonl            ← 操作 journal（每阶段一条，崩溃可续）
  snapshots\<yyyyMMdd-HHmmss-appVer-dshVer>\
      snapshot.json  profile\{package.json, pnpm-lock.yaml, cordis.patch.yml, compatibility.json}
      packages\（可选 full：按 lockfile 完整闭包）
  restore-backup\<operationId>\          ← 每次还原前现场
  reports\report-<op>.json / .md
  logs\loom.log（轮转）
```
profile 位置解析：显式 `--dsh-home` / `--profile-dir` > 环境变量 `DSH_HOME` > `%USERPROFILE%\.dsh`。

### 5.3 进程模型
- 托盘常驻进程持有 **Loom 单实例 mutex**；CLI 检测到已运行时通过本地请求文件 + 结果文件（或单实例 mutex + command queue）交给托盘执行，避免两个进程同时写 profile。
- 只读命令（`status/check/report`）允许独立执行，但必须走同一把 profile 读协调（7.1）。
- 所有写操作按 journal 串行；同一时刻只允许一个写操作。

## 6. 环境适配层

### 6.1 安装定位器（InstallerLocator）
优先级：`config.json.installDir` → 运行中 `DeepSeek Harness.exe` 的 `Path`（按进程名 + 文件名过滤）→ 卸载注册表 `HKCU/HKLM\...\Uninstall` 中 DisplayName/InstallLocation → `app-update.yml` 所在目录推断。
校验：`resources\runtime\primary-runtime\runtime.json`、`resources\runtime\cli\bin\dsh.cmd`、`app.asar\dsh\package.json` 三者存在；失败进入“未找到 DSH”状态（不循环报错），提供“重新定位”。
版本读取：
- **appVersion**：`primary-runtime\runtime.json` 的 `desktopVersion`（失败时用 `app.asar/package.json.version`）。
- **dshVersion**：Electron Node helper 调官方 `getDshRuntimeVersion()`；失败则读 `app.asar\dsh\package.json.version`；再失败标记 unknown。
- 两者分别存储、分别比较；**只有 dshVersion 变化触发插件兼容处理**，appVersion 变化只做提示（P1-1）。

### 6.2 DSH CLI 封装（DshCli）
- 固定使用 `<installDir>\resources\runtime\cli\bin\dsh.cmd`；参数数组直接传（不经字符串拼接），完整记录命令与退出码。
- 运行方式：`& $dshCmd plugin --profile desktop <args>`；显式设置/保留 `ELECTRON_RUN_AS_NODE=1`；cwd 使用安装目录；超时（查询 120s、安装 900s、可配置）；stdout/stderr 流式写日志（脱敏）。
- 失败回退：`DeepSeek Harness.exe --expose-internals <app.asar>\dsh\node_modules\@deepseek-ai\dsh-desktop-host\lib\cli.js`（仅在 dsh.cmd 缺失时）。
- 禁止调用系统 pnpm；辅助重装仍走 `dsh.cmd plugin ...`。安装参数带 `--save-exact`（与 DSH 官方升级路径一致）。
- **锁纪律**：guard 自己写 `package.json` 时持有 `package.json.lock`；调用 `dsh.cmd plugin` 前必须释放该锁（CLI 内部会再次加锁，嵌套会死锁）；整个“读—改—调用—再读”用 journal 串联。
- 若 App 正在运行且命令需要写 `node_modules`：不执行，转为“等待退出/提示”。

### 6.3 Electron Node helper（Evaluator 桥）
- 以脚本文件方式运行：`<installDir>\DeepSeek Harness.exe` 在 `ELECTRON_RUN_AS_NODE=1` 下执行 `helper.mjs`（不要用 `-e`，不要交给系统 Node；不要依赖 `runtime\bin\node.cmd`）。
- helper 输入：JSON（manifest、exemptions、runtimeVersion、静态检查请求）；输出 JSON（官方判定/静态检查结果）。
- 导入官方模块时按候选路径探测（`app.asar\dsh\node_modules\@deepseek-ai\dsh-app-boot\lib\index.js` 等），读取导出并记录 `engine: official`；失败则用自包含 fallback（见 10.1）并记录 `engine: fallback`；两者都失败 → `unknown`。
- helper 有 30s 超时；崩溃不影响主流程，按 fallback 处理。

### 6.4 App 进程检测与安全退出
- 通过 `Get-Process` 按 `ProcessName`（`DeepSeek Harness`）并按 `Path` 归属 installDir 过滤，**包括托盘后台进程**；要求连续 2～3 秒无可归属进程才算“完全退出”。
- 不自动 kill。UI 给出“请从 DSH 托盘菜单完全退出”的引导 + “我已退出，重试”按钮；高级“强制结束”需二次确认并提示会话数据风险。
- 装包前再检查一次进程；发现运行中则中止本次操作、写 journal、回滚已改文件。

### 6.5 更新器缓存（只读）
只读展示 `%LOCALAPPDATA%\@deepseek-aidsh-desktop-updater\` 占用（本机约 586MB：`installer.exe` + `pending` 安装包），提供“打开目录”按钮；不删除 DSH 文件、不复制安装包进快照（P2-1）。

## 7. 一致性、锁与状态

### 7.1 锁矩阵
| 锁/文件 | 持有者 | 典型时长 | Loom 的动作 |
|---|---|---|---|
| `<profile>\lock`（内容为 PID） | 桌面端 `applyRelease` / `disableAllPlugins`（启动与恢复期） | 秒级 | 检测到存在且 PID 存活 → 只读等待；不写入；超时 60s 后转“稍后重试” |
| `<profile>\package.json.lock`（`withFileLock`） | 插件管理器 / `dsh.cmd plugin` 写 manifest | 单次操作（CLI 最长等 120s） | Loom 写 manifest 时持有；**调用 dsh.cmd 前必须释放**；读等待最多 60s |
| `<profile>\.plugin-manager\run.json` | 上一次 pnpm 进程的孤儿记录 | 由 pnpm 生命周期决定 | snapshot/restore 前检查；存在存活 PID 则等待/放弃；死 PID 按 DSH 规则清理需谨慎（只读提示优先） |
| Loom 单实例 mutex | 托盘进程 | 常驻 | CLI 检测到已运行 → 提交命令队列；只读命令可独立执行 |
| 操作 journal | Loom 自己 | 毫秒级 | 串行化写操作；同一时刻仅一个写事务 |

### 7.2 快照读协议（防 torn snapshot）
1. 等待 `profile\lock`、`package.json.lock` 消失，且 `.plugin-manager\run.json` 无存活 PID；
2. 记录基线哈希：`package.json`、`pnpm-lock.yaml`、`cordis.patch.yml`；
3. 读取依赖清单 + 各插件 manifest + bundles + 可选 patch 内容；
4. **再读一次**上述基线文件，哈希与步骤 2 一致才落盘；不一致则指数退避重试（20ms→2s，总上限 60s）；
5. 落盘后再校验快照内 JSON 可解析、哈希与元数据一致；
6. 采集期间若出现锁或 App 正在执行插件操作 → 放弃并记录“环境忙”，不写半成品。
- 采集不要求 App 关闭（只读），但**写 manifest 的还原操作**需满足第 7.1 的锁纪律；包级操作要求 App 完全退出（6.4）。

### 7.3 state.json / config.json / journal
- `config.json`：`schemaVersion`、`installDir`、`dshHome`、`autoUpgradePolicy`（A/B/C）、`allowMajorUpgrade`（默认 false）、`keepSnapshots`（默认 5）、`dataRoot`、`notify`、`quietHours`、`autostart`、`logLevel`。
- `state.json`：`schemaVersion`、`lastSnapshot`（路径+appVersion+dshVersion+sha256）、`preUpdateSnapshot`（冻结指针）、`pendingUpdate`（目标版本、installer 文件名与 sha512、检测时间）、`handledUpdate`、`lastOperation`（id/stage/result）、`toolVersion`。
- **原子写**：临时文件 + rename；写入前校验 JSON；损坏时备份为 `.corrupt-<ts>` 并重建（不丢备份目录）。
- **操作 journal**：每次写事务 `journal\<opId>.jsonl` 逐阶段追加 `start/stage/done|failed`，字段含 opId、阶段、命令、退出码、before/after 哈希、备份路径。启动时若发现未完成 op：先进入恢复流程（回滚或续跑），禁止直接开新写操作。
- `schemaVersion` 迁移函数：旧版本启动先备份 config/state 再升级；失败回退原文件并提示。

### 7.4 单实例与命令队列
- 托盘进程创建命名 mutex；CLI 发现已运行：写 `queue\<uuid>.request.json`（命令+参数），托盘轮询执行并写回 `*.result.json`；CLI 等待结果（超时 120s）。避免两进程同时写 profile。
- 托盘退出时清理 queue；未处理的请求返回 `E_BUSY`。

## 8. 更新时序、触发与状态机

### 8.1 真实更新链路（v2 依据实测）
| 阶段 | 实际行为 | Loom 可观测信号 |
|---|---|---|
| 下载开始 | 更新器写 `pending\temp-<fileName>` | 文件出现（**最早可用的提前量**） |
| 下载完成 | rename 成最终 `<fileName>`，写 `update-info.json`（含 sha512） | 文件更名/出现（兜底） |
| 应用内确认 | DSH 立即调 `updates.install()`，用户确认后 `quitAndInstall(true,true)` | 窗口确认（无法可靠 hook，只能靠前述信号） |
| 安装并重启 | NSIS 带 `--updated --force-run`，装完立即启动新版本 | 旧进程消失后立刻出现新进程；**无稳定空窗** |

**“三次启动”定义（承诺写清楚）**：
1. 更新后新版本自动启动（可能插件被禁用）——Loom 只做检测、提示、文件级修复计划；
2. 用户**完全退出** DSH（托盘图标也退出）；
3. Loom 在 App 退出后完成包级升级/还原，然后启动 DSH（Loom 可代为启动或提示用户启动）。
→ 不承诺“无需额外退出的全自动”。

### 8.2 快照触发矩阵
| 触发 | 条件 | 动作 | 说明 |
|---|---|---|---|
| App 稳定启动 | 启动后 60s 且无锁、无未完成 op | `snapshot --auto`（仅变化才写） | 建立/更新基线；**版本变化时禁止覆盖上次好快照** |
| profile 变化 | package.json/patch/lock 变化后 debounce 30～60s | 同上 | 复用 7.2 读协议 |
| `pending\temp-*` 出现 | 新文件且文件名版本 > 当前 appVersion | `snapshot --full --pre-update` | 取最早提前量；冻结为 pre-update 快照 |
| 最终 `update-info.json` 出现 | 兜底（可能只剩几秒） | 轻量快照（不打包） | 若 pre-update 已存在则跳过 |
| 手动 | 托盘/CLI | `snapshot [--full]` | 用户主动保障 |
| 更新后首次启动 | appVersion/dshVersion 变化 | **只检测与报告，不写新快照** | 先处理后冻结；成功且稳定后才写新基线 |

### 8.3 pending 去重与冻结规则
- 读 `update-info.json`：目标版本、fileName、sha512；与 `state.pendingUpdate`/`handledUpdate` 比较；
- 文件名版本 ≤ 当前 appVersion、或 sha512 已处理过 → 忽略，不产生“待更新”状态、不触发快照；
- 记录 `preUpdateSnapshot` 指针后，在更新处理完成前**任何自动快照都不得覆盖它**；新快照写入新目录，清理策略保护该指针。

### 8.4 更新后状态机
```
idle → snapshotReady → updateDetected → newVersionRunning → awaitingAppExit
                              │                                   │
                              ├─ 仅 appVersion 变化 → 仅提示 ───────┘（结束）
                              ▼                                   ▼
                         checkAndPlan ───────────────► upgrading → verifying → done
                              │                                   │
                              └─ 无可升级/需人工 ─► blocked（托盘黄，等待用户）   └─ 失败 → failed（可重试/回滚）
```
每态定义（托盘文案 / 可用按钮 / 超时 / 重试）：
| 状态 | 托盘提示 | 按钮 | 超时/降级 |
|---|---|---|---|
| updateDetected | “检测到新版 DSH，正在评估插件” | 打开报告 | 10s 后进入 checkAndPlan |
| newVersionRunning | “新版已启动；兼容检查中” | 打开报告 | — |
| awaitingAppExit | “需完全退出 DSH 后升级 N 个插件” | 我已退出，重试 / 稍后 | 用户不退出则保持，最多每天提醒 1 次 |
| upgrading | “正在升级/还原（勿关闭 DSH）” | 取消（安全点） | 单包 15min、总 30min；超时终止 pnpm 并回滚 |
| verifying | “校验中” | — | 30s |
| blocked | “有 N 个插件需人工处理” | 打开报告 / 重试 / 打开插件管理器 | 保持 |
| failed | “更新处理失败，已回滚” | 打开报告 / 重试 / 回滚 | 保持 |

### 8.5 恢复流程证据检测
- 每次启动检查 snapshot 目录与 profile：
  - 强证据：存在 `cordis.patch.yml.bak-*`（mtime 在本次更新窗口内）；或 bundles 等于当前 `WEB_PROFILE.bundles` 基线；或 `operations.jsonl` 有对应 disable 记录；
  - 中证据：新 `crash-*.log` 且内容匹配 host 启动失败（`phase: startup`/error 含 host exit）；关机类 crash 不算；
  - 弱证据：用户手动报告。
- 只有强证据才允许自动还原；中证据只读 check + 提示；弱证据需用户确认。

## 9. 快照规格

### 9.1 snapshot.json（schemaVersion 1）
关键字段：
```
schemaVersion, takenAt, trigger(auto|pre-update|manual|post-update), appVersion, dshVersion,
installDir, profileDir, dshHome,
profile: { bundles:[{name, class: baseline|official|third-party, version, manifestPath}],
           dependencies:{name:{spec, resolved, integrity}}, patch:{sha256, file, backups:[...]},
           compatibility:{file, exemptions:{}} , lockfile:{sha256}},
plugins: [ { name, version, source, dir, engines, peerDependencies, dsh:{bundle, client, platforms},
             static: {patchFiles, clientInject, entryRefs, result: ok|unverified|missing},
             compatibility: ok|incompatible|unverified|unknown, requirements } ],
files: { package.json, pnpm-lock.yaml, cordis.patch.yml, compatibility.json (若有) },
packageArchive: { kind: none|lockfile-closure, files:[{path,sha256,size}] },
environment: { platform, arch, nodeVersion, electronVersion, toolVersion }
```
- **完整性校验**：`snapshot.json` 自身写入后计算 sha256 存入 `state.lastSnapshot`；还原前先校验。

### 9.2 full / light
- **light**（默认自动）：profile 配置文件 + 依赖/插件元数据；体积小、可频繁。
- **full**（更新前/手动）：额外按 lockfile 完整闭包归档（所有顶层依赖的传递依赖），不复制安装包；归档上限默认 500MB，磁盘不足自动降级 light 并提示。
- 归档不依赖 `pnpm pack` 的 prepack 行为：直接从 profile `node_modules` 读取并在快照目录保存 tarball（`tar.gz` 由系统 tar/7z 生成）或保存 `node_modules` 目录清单+文件副本；恢复优先走 lockfile（12.5）。

### 9.3 保留、配额与磁盘
- 保留规则：**pre-update 快照（冻结）永远优先**；最近 5 份；每个 dshVersion 至少 1 份；总配额默认 1GB（可配置）。
- 淘汰顺序：最旧的、非冻结、非当前版本基线 → 顺序删除；报告中展示占用与淘汰记录。
- 每次快照前检查磁盘剩余（至少 2× 预计大小）；不足则跳过 full、写警告。
- `logs\loom.log` 按大小 5MB×3 轮转；`reports\` 保留最近 90 天/100 份。

### 9.4 损坏与回滚
- 快照写入后校验 JSON/哈希；失败文件移到 `snapshots\corrupt-<ts>\`，不作为 `lastSnapshot`。
- 还原前把当前 profile 核心文件复制到 `restore-backup\<opId>\` 并记录哈希；回滚只回滚该 op。

## 10. 兼容性判定

### 10.1 engine 选择：official → fallback → unknown
- **official**：Electron Node helper 导入 `@deepseek-ai/dsh-app-boot`，调用 `getDshRuntimeVersion()` / `evaluatePluginCompatibility(manifest, exemptions, runtimeVersion)`；记录 `engine: official` 与 app-boot 版本。
- **fallback**：官方导入失败时，用自包含实现（vendored semver 规则，与官方一致）：结果记录 `engine: fallback`；fixtures 必须与官方对拍（当前三插件、prerelease、workspace、非法 range、空字段）。
- **unknown**：两者都失败、或 manifest 解析异常 → `unknown`；**unknown 绝不视为兼容**（不自动升级、不自动宣告成功）。

### 10.2 规则边界（与官方一致）
| 字段/情形 | 规则 |
|---|---|
| `engines.dsh` 存在 | 只用它；peerDependencies 不再参与 |
| 无 `engines.dsh` | 检查全部 `@deepseek-ai/dsh` 与 `@deepseek-ai/dsh-*` peer 范围 |
| optional peer（peerDependenciesMeta） | **不豁免**，仍参与 checks |
| 其它 peer（`@deepseek-ai/cordis`、schemastery、react 等） | 忽略 |
| prerelease | `includePrerelease: true`（nightly 场景） |
| `engines.dsh` 为 `workspace:*` 等 | 视为不满足 |
| peer 为 `workspace:^/~/*` | 视为当前 runtime |
| 空/非法 range、非法 engines/peer 字段、缺失 name/version（不匹配时） | evaluator 抛错 → `unknown` |
| `dsh.bundle.platforms` | 独立检查；不包含 `win32` → 不兼容（平台原因） |

### 10.3 静态预检（manifest 判不到的部分）
- `dsh.bundle.patch`：文件存在、可解析为 patch 列表；插入的 `name` 可解析（忽略 `cordis:*` 与相对路径）；
- `dsh.client.inject`：每个包名在目标 runtime 的 node_modules 中可解析（只读探测）；不可解析 → `unverified`；
- `dsh.bundle.platforms` 包含 win32；
- 任一无法确认 → 结果 `unverified`，报告中写明原因；`unverified` 不自动升级、不宣告“成功”。

### 10.4 结果分级与展示
`compatible` / `incompatible`（列出未满足项）/ `unverified` / `unknown`。托盘与报告分别统计；不兼容与未知都进入“需处理”，但处理方式不同（前者升级/豁免/跳过，后者只给报告与人工入口）。

### 10.5 版本豁免生命周期
- 只通过 `dsh.cmd plugin --profile desktop allow-version <pkg@ver> --dsh-version <ver> --accept-risk` / `revoke-version` 写；不要直接改 `compatibility.json`。
- 旧版本豁免：标记 `inactive`（保留记录），提供“清理旧豁免”按钮；不自动授予新版本。
- `rewritable:false`（文件损坏）→ 不覆盖、提示手工修复。
- 崩溃循环防护：同一插件连续 2 次首启失败/崩溃 → 进入 `isolated`（不自动恢复、不重复提示），仅报告与人工入口。
- 每次启动最多提示一次；用户选择“跳过”后本次生命周期内不再打扰。

### 10.6 首启健康检查（升级/还原后）
- 新版本启动后 N 秒（默认 20s）检查：host 进程存活、无新增 startup 类 crash、可探测的本地 HTTP 服务返回 200（若可获得 URL）；
- 失败/超时 → 标记 `verify-failed`，自动回滚本次升级/还原（恢复 restore-backup），并在报告中说明；
- 无法验证 UI 的（如 client 注入不可测）→ 保持 `unverified` + 提示“请确认插件界面正常”。

## 11. 策略 A：自动升级决策表

### 11.1 输入与候选规则
输入：包名、已装版本、原始 spec、目标 dshVersion（更新后的运行时；下载期预下载时用 update-info 目标版本）、profile 的 npm 配置、是否允许 prerelease（nightly 默认允许匹配）、是否允许 major（默认否）。
候选筛选（按顺序）：
1. `semver.gt(v, installed)`；
2. 排除 deprecated（除非无其它候选且用户确认）；
3. 若是 bundle 插件，必须有 `dsh.bundle`；`dsh.bundle.platforms` 含 win32；
4. 以**目标 dshVersion** 调 evaluator，结果必须 `compatible`（fallback/unknown 不入选）；
5. 静态预检：`unverified`/`missing` 不入选自动升级（只进报告）；
6. 排序：稳定版优先 → 版本号降序 → 同版本按 registry 返回顺序；
7. 上限：最多检查 20 个候选版本、每次 lookup 60s 超时、总计划 5min；失败不无限重试。
结果：
- 命中 → 记录候选与选中原因 → `dsh.cmd plugin --profile desktop add <pkg>@<ver> --save-exact`；
- 未命中 → 状态 `blocked`、托盘黄、报告“无兼容版本”，给出三选一：手动升级 / 保留旧版并风险豁免（需二次确认）/ 跳过。

### 11.2 registry 查询（不绕过用户配置）
- 通过 `dsh.cmd plugin --profile desktop view <pkg> versions dist-tags --json` 在 profile 环境执行，复用其 pnpm、`.npmrc`、registry plan（私有源优先、镜像 fallback）、认证与代理；
- 记录查询使用的 registry/耗时；**日志脱敏**（`_authToken`、`Authorization`、URL query）；
- 私有源不可达不自动回退公网；离线/超时快速失败并分类（network/auth/not-found/timeout）；
- 不在没有用户同意时把私有包名发到公网。

### 11.3 安装与顺序
- 一次只装一个包；顺序：普通第三方插件 → `dshmarket` **最后**（失败不影响安全网，P2-2）；
- `--save-exact`；以 CLI 写回的 `package.json`/lock/bundles 为准，guard 只校验 + 记录，不重复写（避免顺序/重复问题）；
- 安装前检查：磁盘空间（store + profile 至少 2× 预估）、App 已完全退出（6.4）、无并发 journal；
- 安装后校验：manifest 版本、bundles 包含、lockfile 与 package.json 一致、evaluator 复检。

### 11.4 major / prerelease / 数据风险
- major 升级默认 **不自动**（`config.allowMajorUpgrade=false`）；提示“可能涉及插件数据格式迁移”，需用户确认；
- nightly 允许 prerelease，但选择顺序仍稳定版优先；
- 用户选择“暂不备份插件数据”，所以 major 升级前报告中必须给出数据风险提示与“先手动备份”的链接。

### 11.5 审计记录（report.json + journal）
字段：operationId、时间、包名、已装版本、候选列表（版本、是否 deprecated、evaluator 结果与原因、static 结果）、选中的 registry/integrity、命令与退出码、安装前后版本、耗时、失败分类、回滚路径。

### 11.6 失败、回滚与离线
- 分类：network/auth/not-found/peer-conflict/disk/permission/timeout/verify-failed；
- 安装失败：`dsh.cmd` 自身会恢复 `package.json`/`pnpm-lock.yaml`；guard 再执行一次 `install --offline --frozen-lockfile` 修复 node_modules，失败则回滚到操作前备份；
- 进程超时/取消：终止 pnpm 进程树（按 PID 记录）、清理/保留 `run.json`（按 DSH 规则），写 journal；
- 离线：不做 registry 查询，直接报告“无法查询/离线”；如策略 A 已排队则不执行；
- 安装到一半崩溃：下次启动读 journal，进入 `repair`（先 `install --offline --frozen-lockfile`，再校验），不要开新操作。

## 12. 还原规格

### 12.1 bundle 三类与还原目标
| 类别 | 例子 | 还原目标 |
|---|---|---|
| 安装包基线 | `@deepseek-ai/dsh-base`、`@deepseek-ai/dsh-web-app` | 始终以**当前安装包模板**为准，不用快照旧值 |
| 官方可选 | `@deepseek-ai/dsh-experimental-agent-team-profile` 等 | 若快照中存在且当前不在 → 视为被恢复流程移除，候选还原（需证据） |
| 第三方 | `dshmarket`、插件 | 按还原规则（12.3/12.4）处理 |
还原集 = 快照中的“非当前基线集合”，不是“第三方集合”。

### 12.2 恢复证据分级
| 级别 | 证据 | 动作 |
|---|---|---|
| 强 | `cordis.patch.yml.bak-*`（时间在更新窗口）、bundles 等于 `WEB_PROFILE.bundles`、operations.jsonl 有 disable 记录 | 允许自动文件级还原 |
| 中 | 新 crash 且 `phase: startup`、error 匹配 host 启动失败 | 只读 check + 提示，等待用户确认 |
| 弱 | 用户报告、界面异常 | 用户确认后处理 |

### 12.3 合并规则
| 对象 | 规则 | 冲突处理 | 报告分类 |
|---|---|---|---|
| `dsh.profile.bundles` | 以快照顺序为基准；基线取当前安装包；已存在的保持位置；缺失的按快照相对顺序插入；幂等 | 用户更新后新装的 bundle 保留在末尾 | 已还原/已跳过 |
| `dependencies` spec | 包存在则保留当前 spec/版本；缺失才补快照 spec | 当前版本更新（用户升级过）→ 保留当前 | 已跳过 |
| `pnpm-lock.yaml` | 能恢复则恢复；与 package.json 不一致时先 `install --lockfile-only` 修复 | 不覆盖用户新 lock 中的新依赖 | 已还原 |
| `cordis.patch.yml` | 优先级：`.bak-*`（若比快照新）> 快照 > 当前；当前非空且与两者都不同 → 输出 diff，默认保留当前 | 用户选择 | 冲突待处理 |
| `compatibility.json` | 只恢复**精确匹配当前 dshVersion** 的豁免；旧版本标记 inactive | 损坏文件不覆盖 | 已还原/失效 |
| `.dsh-market/state.json` | 默认不还原（属于市场/用户偏好），仅报告 | — | 已跳过 |

### 12.4 “缺失”与“用户主动删除”的区分
- 依赖仍在 `dependencies`、包仍在 `node_modules`、只是不在 bundles → **视为用户禁用**，不自动加回；
- 依赖与包都不存在 → 视为“未安装”，不自动加回；
- 依赖在、bundles 缺、且存在强恢复证据（12.2）→ 视为被恢复流程移除，可还原；
- 可选辅助：`.dsh-market/state.json`、operations.jsonl 最近操作时间；不确定时只提示，不写。

### 12.5 包级恢复顺序（App 完全退出后）
1. 恢复 `package.json` + `pnpm-lock.yaml`（快照值，保留用户新增字段）；
2. `dsh.cmd plugin --profile desktop install --offline --frozen-lockfile`（最快、可复现；需要 store 有缓存）；
3. 离线失败且用户同意 → 联网 `install --frozen-lockfile`；
4. 仍失败 → 仅对缺失包使用归档 tarball（**最后手段**）；安装后必须把依赖 spec 改回原 registry spec 并重建 lock（或恢复原 lock 后 `--lockfile-only`），不允许残留 `file:`；
5. 归档必须按 lockfile 生成**完整闭包**（顶层依赖的全部传递依赖），不是只 pack 顶层包；不依赖 `pnpm pack`/prepack。
注：`dsh.cmd plugin install` 是否支持 `--offline --frozen-lockfile` 在 spike 中验证；若不支持，用 bundled pnpm 直接执行并记录（仍不调用系统 pnpm）。

### 12.6 验证、回滚、首启失败判据
- 还原后校验：JSON 可解析、bundles/依赖存在、manifest 版本、evaluator 复检、可选 `dsh --dump-config`（若可用）。
- 回滚：只回滚当前 op，用 `restore-backup\<opId>`；回滚后再次校验。
- **首启失败判据**（任一）：新版本启动后 host 未 ready（N 秒）、进程提前退出、产生 startup 类新 crash、check 仍发现 bundles/依赖缺失。失败 → 自动回滚本次升级/还原，标记 `verify-failed` 并报告；不把用户手动崩溃误判为修复失败（对比 crash 时间窗口与 op 时间）。

### 12.7 幂等与报告
- 所有写操作幂等：按 key 去重、按原顺序插入、重复 restore 不重复添加。
- 报告三分类：已还原 / 已跳过（用户改动）/ 冲突待处理；同时输出 `report.json`（机器可读）。

## 13. 托盘 / UI / 交互

### 13.1 实现选型（P1-15 决策）
- **主实现：.NET 10 WPF（C#）+ WinForms NotifyIcon，自包含单文件 exe（win-x64）**；CLI 与托盘同一 `loom-dsh.exe`（`loom-dsh snapshot/check/restore/...`）。
- 选型理由：本机已具备 .NET 10 SDK（10.0.300）与 WindowsDesktop 运行时（10.0.8），WPF 能直接实现设计稿的卡片/弹层/深浅主题；自包含发布后最终用户无需安装 .NET。
- 构建：`dotnet publish -c Release -r win-x64 --self-contained true /p:PublishSingleFile=true`；WPF 不支持 NativeAOT/trimming，保持默认裁剪策略；产物约 100–150MB，压缩后分发；可选 ReadyToRun 提升启动速度。
- 设计稿作为视觉规范：首版实现托盘弹层 + 设置窗 + 通知 + 兼容提示卡；**不承诺像素级 1:1**（backdrop blur/噪点等效果降级实现），验收以信息架构、状态、交互为准。
- 备选：框架依赖发布（体积小但用户需装 .NET 10 Desktop Runtime），不作为默认；PowerShell 仅保留诊断/一次性脚本，不作为主程序。
- UI 需 DPI-aware（PerMonitorV2）与系统深/浅主题切换（跟随系统，可手动覆盖）。

### 13.2 托盘状态

|---|---|---|---|
| 正常 | 彩色/深底对钩 | 最近快照时间 | 立即快照/检查/报告/设置/退出 |

## 18. 风险、未决与不做

### 18.1 主要风险
| 风险 | 影响 | 缓解 |
|---|---|---|
| client/patch 兼容性无法完全静态判定 | 升级后 UI 白屏/功能失效 | static precheck + unverified + 首启健康检查 + 回滚 |
| 自动更新无稳定空窗 | 策略 A 必须多一次退出 | 状态机 + 明确三次启动承诺 + 托盘引导 |
| DSH 未来版本改路径/导出/打包 | evaluator 失效 | official/fallback/unknown 三级 + 自包含 fallback + 对拍测试 |
| 用户更新后手动改动被覆盖 | 用户反感 | 证据分级 + 合并规则 + 默认不覆盖 + 冲突给 diff |
| major 升级数据格式变化 | 配置丢失 | major 需确认 + 风险提示 + 可选数据备份 |
| .NET 10 WPF 体积/启动/杀软 | 自包含 exe 体积大、SmartScreen 提示 | 单文件 + 可选 ReadyToRun；提供 SHA256/说明；二期签名 |
| 杀软/签名 | 启动被拦 | 绿色目录 + 说明 + SHA256；二期签名 |
| 私服/离线 | 策略 A 不可用 | pnpm 配置查询 + 离线降级 + 人工入口 |

### 18.2 需 spike 确认的未决项
`dsh.cmd plugin install --offline --frozen-lockfile` 是否支持；真实更新各时间点；.NET 10 WPF 单文件发布/DPI/主题/自启；Toast AUMID 是否必须；`Get-Process` 对 DSH 后台进程的识别完整性。

### 18.3 不做
自动 kill DSH；自动风险豁免；修改安装目录/app.asar；备份插件业务数据；处理 web 等其它 profile；自动 major 升级；删除更新器缓存。
