> `docs\实现方案-v2.md`，审核问题闭环见其第 19 节。本文件仅保留决策痕迹。

> 版本：初稿 | 环境：DeepSeek Harness 桌面版 0.2.2-rc.1（Electron 44.7.0，nightly 频道），Windows x64
> **2026-11-14 审核后勘误：本文若干路径/命令/时序假设已被独立审查推翻，修正见第八节（编码前必读）；未修改的正文保留原状以保留决策痕迹。**
> 结论先行：**插件本体和配置其实都在 `~/.dsh/profiles/desktop`（安装目录之外），更新本身不会删。**
> 真正让插件"像没装一样"的是 DSH 的**版本兼容性拦截**和**启动失败恢复流程**。所以方案 = 快照保险 + 自动还原配置/启用状态 + 用官方逻辑做兼容预检并提示处置。

### 为什么"更新后插件都要重装"——已从桌面端与 dsh 源码确认的三条真实机制

**A. 兼容性拦截（最可能的主因）**
DSH 启动装载 profile 时，会对每个 bundle / 插件行做 semver 检查：
- 插件 `package.json` 若有 `engines.dsh` → 只用它判断；
- 否则检查 `@deepseek-ai/dsh`、`@deepseek-ai/dsh-*` 的 `peerDependencies` 范围；
- 不满足 → 该 plugin 行被标记 `disabled`（日志 `disabling profile plugin ...`），bundle 则被跳过（`skippedBundles`）。
> 位置：`@deepseek-ai/dsh-app-boot` 的 `evaluatePluginCompatibility` / `loadProfileDirectory` / `prepareProfileEntries`。
> 更新让 DSH 版本变化后，旧插件可能瞬间"消失/失效"，于是只能在插件管理器里重装（通常是升到兼容版本）。

**B. 启动失败后的「禁用第三方插件」恢复**
host 崩溃时桌面端弹窗按钮：退出 / 重启 / **禁用第三方插件** / 获取诊断报告。
点"禁用第三方插件"会：① `cordis.patch.yml` 备份成 `cordis.patch.yml.bak-<时间戳>`；② `dsh.profile.bundles` 重置为内置基线；③ 包保留在 `node_modules` 但不再启用，重启应用。
> 效果 = UI 里插件全部显示"未安装"，用户必须重新添加 → 完全符合"每次更新都要重装插件"的描述。

**C. 安装期版本拒绝**
插件管理器/`dsh plugin` 安装时会预检兼容性，不兼容直接拒绝（退出码 1），并提示可用精确版本豁免（`allow-version`）承担风险。"重新安装"实际经常是"升级到兼容版本"。

### 已经确认可复用的官方能力（不用自己发明兼容规则）

| 能力 | 入口 |
|---|---|
| 兼容性判定（与 DSH 启动完全一致） | `@deepseek-ai/dsh-app-boot` 的 `evaluatePluginCompatibility(manifest, exemptions, runtimeVersion)`、`getDshRuntimeVersion()`（**已验证可直接从 app.asar 导入并跑通**） |
| 精确版本风险豁免 | profile 下 `compatibility.json`，格式 `{"包名@精确版本": ["精确DSH版本"]}`；CLI：`dsh plugin allow-version <pkg@ver> --dsh-version <ver> --accept-risk`；插件管理器 `set_version_exemption` |
| 本地离线安装 | `dsh plugin --profile desktop add file:<tgz或目录>`（pnpm 支持 tarball / 绝对路径；安装前仍会做兼容预检） |
| 环境隔离 | `DSH_HOME` 环境变量可覆盖，便于干跑测试 |
| 并发保护 | profile `package.json` 有跨进程文件锁；安装操作必须避免与应用内操作冲突 |

## 二、方案总览

```
┌────────────────────── 更新前（自动/手动） ──────────────────────┐
│  snapshot：插件清单+精确版本+来源、package.json、patch、           │
│            compatibility.json、pnpm-lock、插件包归档（离线）       │
│  存储：%USERPROFILE%\.dsh\plugin-backups\<ts>-app<ver>\           │
└────────────────────────────────────────────────────────────────┘
                              │ 用户更新 App（nightly）
                              ▼
┌────────────────────── 更新后（计划任务/启动包装器） ─────────────┐
│  1) 版本变化检测：runtime.json 的 desktopVersion ≠ 快照 dshVersion │
│  2) check：逐插件兼容性判定（复用官方 evaluator）                  │
│       ├─ 全部兼容 → 静默（或提示"已就绪"）                         │
│       └─ 有不兼容 → 提示 + 报告：升级 / 风险豁免(人工确认) / 跳过   │
│  3) restore：只补齐丢失项，不覆盖用户新改动                        │
│       - 文件级：bundles/deps 条目、patch（冲突给 diff）、豁免(仅同版本)│
│       - 包级（罕见）：本地 tgz / pnpm store 离线重装（App 退出时）  │
│  4) 结果报告 + 提示重启生效；每次还原前保留当前快照以便回滚         │
└────────────────────────────────────────────────────────────────┘
```

**核心策略：**
1. **不碰安装目录**，只守护 `~/.dsh/profiles/desktop`；不做侵入式补丁。
2. **文件级还原为主**（绝大多数情况包还在 `node_modules`，只需要把 bundles/配置放回），**包级离线重装为兜底**。
3. 兼容性判定**复用 DSH 官方模块**，保证与启动行为 100% 一致；风险豁免**永不静默**，必须人工确认。
4. 所有写操作**先备份、有锁、可回滚、有报告**。

## 三、详细设计

### 3.1 快照（"提取"）内容与格式

目录：`%USERPROFILE%\.dsh\plugin-backups\<yyyyMMdd-HHmmss>-app<应用版本>\`

```
snapshot.json                  # 主清单（见下）
profile/package.json           # 原样复制
profile/cordis.patch.yml       # 用户配置层
profile/pnpm-lock.yaml
profile/compatibility.json     # 若存在
profile/.dsh-market/state.json # 市场启用/分组状态（可选）
packages/<pkg>@<ver>.tgz       # 每个第三方插件及其依赖的离线归档（可选，P2）
plugins-data/                  # 可选：~/.dsh 下插件私有数据目录快照
report.md                      # 快照摘要（人类可读）
```

`snapshot.json` 建议结构：

```json
{
  "schemaVersion": 1,
  "capturedAt": "2026-11-14T10:46:00+08:00",
  "appVersion": "0.2.2-rc.1",
  "dshVersion": "0.2.2-rc.1",
  "platform": "win32-x64",
  "profile": {
    "dir": "C:\\Users\\<user>\\.dsh\\profiles\\desktop",
    "bundles": ["@deepseek-ai/dsh-base", "@deepseek-ai/dsh-web-app",
                "@deepseek-ai/dsh-experimental-agent-team-profile",
                "dshmarket", "dsh-plugin-wallpaper-engine", "dsh-whale-widget"],
    "dependencies": { "dshmarket": "^1.73.19", "dsh-plugin-wallpaper-engine": "1.4.2", "dsh-whale-widget": "^0.4.2" },
    "patchSha256": "…", "compatibility": { }
  },
  "plugins": [
    {
      "name": "dsh-plugin-wallpaper-engine", "version": "1.4.2",
      "source": "dsh-plugin-wallpaper-engine@1.4.2",
      "installedDir": "…\\node_modules\\dsh-plugin-wallpaper-engine",
      "manifest": { "engines": {"dsh": "^0.2.0-rc.1", "node": ">=22.12.0"}, "peerDependencies": { } },
      "compatibilityAtCapture": "ok",
      "corePackage": false
    }
  ]
}
```

采集方式：读 profile `package.json`，对每个依赖在 `node_modules/<name>/package.json` 读 manifest；用官方 `getDshRuntimeVersion()` 记录当时的 DSH 版本；`packages/*.tgz` 用 pnpm pack 或整目录压缩（P2 再实现）。
保留策略：最近 5 份 + 每个应用版本至少 1 份，总量上限 ~300 MB。

### 3.2 触发时机（关键设计点）

| 时机 | 动作 | 说明 |
|---|---|---|
| 每次 App 启动后（或计划任务每 30 分钟） | `snapshot --auto`：与上次快照比较（插件集合/版本/patch 哈希），**有变化才写新快照** | 不做更新拦截，靠"最后状态"保险；开销小 |
| `%LOCALAPPDATA%\@deepseek-aidsh-desktop-updater\pending\` 出现安装包 | 立即 `snapshot` | 更新下载完成 ≈ 马上要重启安装，是最佳快照点 |
| App 启动（计划任务/启动包装器） | 读 `D:\DeepSeek\resources\runtime\runtime.json` 的 `desktopVersion`，与快照 `dshVersion` 比较；不同 → 进入"更新后处理" | 检测到版本变化即触发 check/restore |
| 发现 `cordis.patch.yml.bak-*` 或新 `crash-*.log` | 标记"疑似走了禁用插件恢复"，直接提示可一键还原 | 恢复流程的直接证据 |

**执行窗口**：文件级还原（小文件）可在 App 运行时进行（遵守 `package.json` 文件锁 + 重试，下次启动生效）；包级重装必须 App 完全退出后执行。计划任务检测到版本变化后：先做只读 check → 提示 → 等 App 退出（或用户确认"立即还原并重启"）→ 还原 → 提示重新打开。

### 3.3 兼容性判定与提示

**判定**：复用 `@deepseek-ai/dsh-app-boot`（已验证可在本机直接 import 跑通）：

```js
const boot = await import('file:///D:/DeepSeek/resources/app.asar/dsh/node_modules/@deepseek-ai/dsh-app-boot/lib/index.js');
const rt = boot.getDshRuntimeVersion();                    // "0.2.2-rc.1"
const issue = boot.evaluatePluginCompatibility(manifest, exemptions, rt);
// issue === undefined → 兼容；否则 issue.requirements 列出未满足项，issue.exempted 表示已有精确豁免
```

判定对象：`dsh.profile.bundles` 里每个 bundle + `package.json` 中全部非内置依赖；另外扫描 `node_modules` 顶层第三方包（防止"漏网"）。
注意：内置 `@deepseek-ai/*` 由安装包提供，不做还原、不做升级。

**提示内容**（写入 `report.md` + Windows toast 摘要 + 控制台）：
```
DSH 已更新 0.2.2-rc.1 → 0.3.0
不兼容插件 2 个：
  dsh-plugin-wallpaper-engine@1.4.2  需要 engines.dsh ^0.2.0-rc.1
  dshmarket@1.73.19                   需要 @deepseek-ai/dsh-settings ^0.1.0-rc.7…
建议：
  [升级] 查询 registry 最新兼容版本 → 一键安装（需联网）
  [豁免] 保留旧版并接受风险（会写 compatibility.json，仅对 0.3.0 生效；需确认）
  [跳过] 暂不处理，仅保留报告
```

**处置**（按用户选择执行，默认"只提示不自动改"）：
1. **升级**：查 registry 该包 `latest`/可用版本列表 → 用同一 evaluator 预检 → 兼容则 `dsh plugin --profile desktop add <pkg>@<ver>`（App 退出时执行）→ 更新 bundles/deps。
2. **风险豁免**：`dsh plugin allow-version <pkg@ver> --dsh-version <新版本> --accept-risk`（等价写 `compatibility.json`），必须用户显式点确认，并提示"可能崩溃/损坏数据"。
3. **跳过**：只保留报告，下次启动仍会被禁用，但不会静默做决定。

### 3.4 还原策略（"放回"）

按顺序、幂等执行，每一步先备份当前文件到 `restore-backup/<ts>/`：

1. **检测差异**：快照 vs 当前 profile——bundles 顺序、dependencies、patch 哈希、compatibility.json、node_modules 里包是否缺失/版本不符。
2. **文件级还原（主要路径）**
   - `dsh.profile.bundles`：把快照中缺失的第三方 bundle 按原顺序插回（内置基线保持当前值，不覆盖新版本的默认基线）；
   - `dependencies`：补回缺失条目（已存在且版本不同的，以用户当前为准并在报告里标注）；
   - `cordis.patch.yml`：当前文件为空/缺失才恢复；有冲突时输出 diff 让用户选（默认保留当前，防止覆盖更新后新调过的配置）；
   - `compatibility.json`：只恢复**同时匹配新 DSH 精确版本**的豁免；旧版本的豁免自动失效并提示；
   - 保留当前文件的备份，生成 `report.md`。
3. **包级还原（兜底，App 退出后）**
   - 优先本地归档：`dsh plugin --profile desktop add file:<snapshot>\packages\<pkg>@<ver>.tgz`；
   - 其次 `pnpm install --offline`（pnpm store 命中）；
   - 最后才联网（用户确认）。
4. **验证**：核对每个插件 manifest 版本、bundles 顺序、`compatibility.json`；输出结果报告；提示"重启 DSH 生效"。
5. **回滚**：`restore --rollback [快照名]` 用 `restore-backup` 恢复还原前状态；首启失败自动回滚（见风险）。

### 3.5 工具形态与命令

- `dsh-guard.ps1`（主入口，配合一个 `guard-helper.mjs` 用 DSH 自带 Node 运行官方 evaluator；无第三方依赖、本地离线）。
- 子命令：
  ```
  dsh-guard snapshot [--full]      # 提取/快照（--full 含插件包归档）
  dsh-guard check                  # 只读兼容性检查 + 报告
  dsh-guard restore [--apply]      # 预览/执行还原（文件级；包级需 App 已退出）
  dsh-guard report                 # 打开最近报告
  dsh-guard install-task           # 注册计划任务（登录时 + 定时检查）
  dsh-guard rollback               # 回滚最近一次还原
  ```
- 目录：
  - 备份：`%USERPROFILE%\.dsh\plugin-backups\`
  - 日志：`%USERPROFILE%\.dsh\plugin-backups\guard.log`
  - 报告：`%USERPROFILE%\.dsh\plugin-backups\report-<ts>.md`

### 3.6 安全与边界

- 只操作 `profiles/desktop`；**不修改安装目录、不修改 app.asar**。
- 写 profile 一律走"备份 → 加锁 → 原子写"；检测到 App 正在运行且需要 pnpm 时，等待退出或提示用户。
- 风险豁免必须人工确认，脚本不提供"自动接受风险"开关（避免误操作导致崩溃/数据损坏）。
- 不备份 `~/.dsh/sessions`、`~/.dsh/attachments` 等无关数据；插件数据目录按需可选备份。
- 报告与日志不落盘敏感信息（不含 API Key 等）。

## 五、风险与未决点

1. **浏览器端（client）兼容性无法只靠 manifest 判定**：patch 引用的 entry id 改名、client 模块 API 变化时，版本检查可能通过但运行异常。→ 还原后首启若崩溃/报错，guard 自动回滚到"禁用"状态并提示。
2. **跨大版本更新（如 0.2 → 0.3）还原救不了旧插件**，只能升级/豁免/禁用；方案会明确提示。
3. **自动更新后会立即自动重启**，无法在首次启动前拦截 → 第一次启动可能短暂缺插件；文件级还原后提示重启一次即可（已确认可接受）。
4. **还原与用户更新后手动改动冲突**：默认"只补缺失、不覆盖现有"；patch 冲突给 diff 由用户决定。
5. 计划任务/开机自启需要用户授权；若不想常驻，也可纯手动：更新前双击 `snapshot`，更新后双击 `check/restore`。

## 六、已确认的决策（2026-11-14）

| 项 | 结论 |
|---|---|
| 更新方式 | **应用内自动更新**（nightly；下载完成后在应用内安装，随后自动重启新版本） |
| 插件范围 | 目前只有插件市场安装的 npm 包（`dshmarket` / `wallpaper-engine` / `whale-widget` 这类）；**无** git 源 / 本地目录 / 手动复制插件；暂不需要备份插件自身的数据设置 |
| 兼容冲突默认动作 | **A：自动查询并升级到兼容版本**（需联网）；查不到兼容版本时降级为"提示 + 人工处理"，不做静默豁免 |
| 更新后需再重启一次 | **可以接受**（首次启动可能短暂缺插件，还原/升级后提示重启一次生效） |
| P0 只读取证脚本 | 暂不做，直接按最终形态实现 |

## 七、最终交付形态（已确认）

### 结论：做「绿色免安装的 Windows 托盘小工具（自带同名 CLI）」，不做 DSH 插件

一个文件夹即整个软件：双击即可运行，不需要安装程序、不需要管理员权限、不改 DSH 安装目录；平时缩在托盘后台，命令行入口是同一份代码的另一种用法。

**为什么不是 DSH 插件（三条硬理由）：**
1. **会被"连坐"**：桌面端崩溃恢复的"禁用第三方插件"会把 `dsh.profile.bundles` 重置为内置基线，插件形态的 guard 自己也从 bundles 里消失，下次启动根本不会加载，救不了任何东西。
2. **宿主运行中不能安全重装包**：更新是应用内安装后自动重启；要执行 pnpm 升级必须等 App 完全退出。常驻在宿主里的插件没有"App 退出后继续运行"的能力。
3. **监控与通知需要进程外能力**：监听更新器 `pending` 目录、安装目录版本变化、`cordis.patch.yml.bak-*` 出现、崩溃日志新增、App 进程退出——这些都在宿主之外，插件做不了。

**为什么不是纯命令行：** 应用内自动更新并自动重启，纯 CLI 没有"被触发"的时机，也不会主动提示；快照必须赶在更新安装前完成，命令行只能靠人手点，容易漏。托盘常驻是唯一能覆盖完整链路的方式。CLI 作为附带的自动化入口保留（方便排查、手动控制和以后接别的工具）。

### 7.3 自动流程（应用内自动更新场景）

```
平时：托盘驻留，轮询「更新器 pending 目录 + runtime.json 版本 + profile 变化」
  └─ 插件集合/版本/patch 有变化才写新快照（开销极小）

1) 检测到新安装包下载完成（pending\ 出现 update-info/installer）
   → 立即 full snapshot（含插件包归档） → 托盘气泡「已备份当前 N 个插件」

2) 你在应用内点安装 → DSH 退出 → 安装器替换 D:\DeepSeek → 新版本自动启动
   （此时旧插件可能已被兼容性禁用/被恢复流程清空，但备份是完整的）

3) 托盘检测到 desktopVersion 变化，进入「更新后处理」：
   ├─ 全部兼容 → 静默/提示恢复 bundles、deps、patch 的缺失项
   │            → 气泡「插件配置已恢复，重启 DSH 生效一次」
   └─ 有不兼容 → 按策略 A 自动处理：
        ├─ 联网查各插件可用版本 → 用官方 evaluator 挑出兼容新版
        ├─ 监测 DSH 进程退出（或托盘点「立即还原/升级」引导退出）
        ├─ 用 `dsh plugin --profile desktop add <pkg>@<ver>`（必要时 file:<tgz> 离线）
        └─ 写回 bundles/deps、恢复 patch → 气泡「已升级 N 个插件，点击启动 DSH」
           （可选设置：恢复完自动启动 DSH）
   └─ 查不到兼容版本 → 气泡 + 报告，提示人工处理（保留旧版需显式风险豁免，绝不自动）

4) 每次动作写 report-<ts>.md；还原前现场存 restore-backup/，可一键回滚
```

### 8.1 必须修正的关键事实（原方案假设有误）

| # | 原方案假设 | 实测/源码事实 | 修正 |
|---|---|---|---|
| 1 | 读 `resources\runtime\runtime.json` | 实际在 `resources\runtime\primary-runtime\runtime.json` | 版本检测改读此文件；同时区分 `appVersion` 与 `dshVersion` |
| 2 | 直接跑 `dsh plugin --profile desktop ...` | PATH 里没有 dsh；普通 CLI 拒绝 desktop profile | 只用 `resources\runtime\cli\bin\dsh.cmd`（Desktop 专用入口，内部带 pnpm） |
| 3 | `pending\` 出现安装包 = 最佳快照点 | 下载期先写 `temp-*.exe`；最终文件出现后用户可能几秒内确认安装；且本机残留 11/7 的 293MB 旧包 | 快照触发改用 `temp-*` 出现/下载开始；按 `update-info.json` 的 sha512+版本去重，不能把"目录存在"当事件 |
| 4 | 更新后会自动重启，可等 App 退出再升级 | `quitAndInstall(true,true)` → 安装器 `--updated --force-run`，装完立即拉起新版本 | "全自动无感"不可实现；明确"最多多一次重启"：新版本启动 → 用户退出一次 → guard 升级 → 再启动一次 |
| 5 | 恢复基线 = 内置 base/web-app，只还原第三方 | `sanitizeProfile(..., WEB_PROFILE.bundles)` 只留 base+web-app，会连 agent-team 一起拿掉 | bundle 分三类：安装包基线 / 官方可选 / 第三方；还原目标是"快照中的非当前基线集合" |
| 6 | 快照/还原只涉及一种 `package.json` 锁 | 实际有三套：`profile\lock`（PID）、`package.json.lock`（120s）、`.plugin-manager\run.json`（孤儿 pnpm） | 补锁矩阵、读一致性协议（双读哈希一致才落盘）、操作 journal、崩溃后续跑 |
| 7 | 包级兜底用 `file:<tgz>` | 会改写依赖 spec 为 `file:`；顶层 tgz 不含 wallpaper 的 8 个子包；`pnpm pack` 受 `prepack` 影响 | 顺序改为：恢复 package.json+lock → `dsh.cmd plugin install --offline --frozen-lockfile` → 必要时联网 → `file:tgz` 仅最后手段且事后恢复原 spec |
| 8 | helper 可用系统 Node 跑 | 系统 Node 无法 import app.asar；`runtime\bin\node.cmd` 依赖未设置的环境变量 | helper 必须跑在 Electron Node 模式（`ELECTRON_RUN_AS_NODE=1` + `--expose-internals`） |
| 9 | 所有插件都能被 manifest 兼容性覆盖 | `dsh-whale-widget` 无 engines/peers，evaluator 恒判"兼容"，但它有 `dsh.client.inject` | 增加静态预检（client inject / patch 可解析）与"未验证"状态；首启健康检查 |
| 10 | 新增 crash 日志 = 走了禁用插件恢复 | 关机时也会写 crash 报告；11/7 那份更像 host 退出 | 恢复证据分级：`.bak-*`（强）> bundles 被重置为基线（强）> crash 内容匹配（中） |
| 11 | 策略 A 有目标即可 | 未定义用当前还是目标 runtime 预检、候选排序、prerelease/deprecated/私服/离线、`--save-exact`、失败回滚与审计 | 补决策表 + 审计字段；major 升级需确认；查不到兼容版本绝不自动豁免 |
| 12 | 交付物 = `guard.ps1` + icon.ico 即可承载设计稿 | PowerShell NotifyIcon 做不出卡片式弹层/设置窗口/深浅主题 | UI 主体实现选型待定：建议 WPF（.NET Framework 4.8 系统内置）单 exe，PowerShell 仅作 CLI/兜底（P1-15） |

### 8.2 P0 补充进方案的要求（实现前必须写清）

1. **快照触发矩阵 + 冻结规则**：App 稳定启动后 / profile debounce 变化 / `pending\temp-*` 出现 / 最终 `update-info.json` 兜底 / 手动；检测到版本变化后**禁止自动写新快照**，避免用"坏状态"覆盖最后一份好快照。
2. **更新-升级状态机**：`idle → snapshotReady → updateDetected → newVersionRunning → awaitingAppExit → upgrading → verifying → idle/failed`，每态定义托盘文案、按钮、超时；完全退出 = 安装目录下所有 `DeepSeek Harness.exe` 进程消失且稳定 2～3 秒；不自动 kill。
3. **CLI 封装**：安装定位器（配置/运行进程/卸载注册表/`app-update.yml` 推断）+ 固定用 `dsh.cmd` 参数数组调用 + 超时/流式日志/退出码；禁止系统 pnpm；锁不嵌套（guard 释放 `package.json.lock` 后再调 CLI）。
4. **一致性协议**：锁矩阵、双读哈希校验、`state.json` 原子写 + schemaVersion + 操作 journal（未完成操作下次启动先恢复/回滚）。
5. **恢复语义**：三类 bundle；恢复证据分级；"用户主动删除"不自动加回；patch 优先用 `.bak-*`，冲突给 diff；报告分"已还原 / 已跳过 / 冲突待处理"。
6. **包级恢复**：`package.json + pnpm-lock` → `pnpm install --offline --frozen-lockfile`；归档按 lockfile 完整闭包；回滚恢复原 spec，不允许残留 `file:`；定义首启失败观测量（host 未 ready / 新 crash / 进程提前退出 / check 仍缺项）。
7. **策略 A 决策表**：候选筛选（>已装、非 deprecated、win32 平台、有 dsh.bundle、目标 runtime 预检通过）、上限与超时、registry 走 profile 的 pnpm 配置、`--save-exact`、失败分类、审计记录、无兼容版本时的三选一（升级/豁免需确认/跳过）。
