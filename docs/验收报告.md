### 2.2 方法（未修改实现代码）

1. **构建/测试**：`powershell -ExecutionPolicy Bypass -File scripts\build.ps1`。
2. **真实环境只读冒烟**：用 Debug 产物依次执行 `status/doctor/snapshot/check/report/restore --dry-run --json`；运行前后对真实 profile 4 个核心文件、安装目录三件套 + exe 计算 SHA256 与 mtime 比对（证据 `evidence/real/before.json`、`after.json`、`drift.txt`）。全程不联网、不写真实 profile/安装目录、不 kill 真实 DSH 进程。
3. **沙箱验收（核心）**：在 `D:\BS\Loom-DSH\.qa-accept\<guid>` 构造假安装目录（`resources\runtime\primary-runtime\runtime.json`、`resources\runtime\cli\bin\dsh.cmd`、空 `resources\app.asar`、`DeepSeek Harness.exe`、`resources\app-update.yml`）与假 DSH_HOME（真实 profile 最小副本：配置文件 + 各依赖 `node_modules\<pkg>\package.json`），通过 `--install-dir/--dsh-home/--data-root` 注入。
   - **版本可控**：为在不触碰真实安装目录的前提下验证 appVersion/dshVersion 分离与兼容性路径，构建了一个 **QA 专用 stub `DeepSeek Harness.exe`**（`.qa-verify/fake-electron`，按 `helper.mjs` 协议回 JSON，读取 `fake-eval.json` 的 runtimeVersion/levels）。它**不替代真实 evaluator 验证**：真实 evaluator 由 116 个单测（含 official↔fallback 对拍、真实 app.asar probe）与真实环境 check（engine=official）覆盖。
   - 破坏性演练全部在副本上：模拟恢复流程（bundles 重置为 base+web-app、`cordis.patch.yml` 改名 `.bak-<ms>`）、用户新增/禁用/改依赖、损坏 `compatibility.json`、锁定文件（活/死 PID）、中文/空格路径。
4. **托盘 Tick 验收**：启动真实 `loom-dsh.exe --tray`（自定义 data root），用一个常驻 stub `DeepSeek Harness.exe` 进程模拟“DSH 正在运行”，按 15s Tick 观察自动快照 / pending 更新 / 版本变化 / 自动还原，并读取 `state.json`、`snapshots/`、`reports/`、`restore-backup/` 断言。
5. **UI**：无托盘进程时执行 `ui render`，核对 6 张 PNG（deep/light × popup/settings/wizard）与 token；再分别冒烟 `ui popup|settings|wizard|report`，确认窗口创建、进程可退出、无残留。
6. **发布**：`scripts/publish.ps1`，用 .NET Process 验证 `dist\loom-dsh.exe version --json` / `status --json` / `doctor --json`，核对 `SHA256SUMS.txt`。
7. **代码审计**：对照设计 §7（锁/一致性）、§8.4（状态机）、§10.5（unknown≠兼容）、§12（合并/回滚）、§13（UI）、§15（安全）逐文件审查；对关键缺陷做了可复现的沙箱实验。

> 说明：QA 脚本放在 `.qa-verify/`（非实现目录）；沙箱与证据目录 `.qa-accept/`、`.qa-verify/evidence/`。未修改 `src/Loom*` 任何实现文件。PowerShell 5.1 读取无 BOM 的 UTF-8 `.ps1` 会按 ANSI 解码导致中文/引号解析错误，QA 脚本统一保存为 UTF-8 **带 BOM**（仅测试脚本，不影响产品）。

## 六、缺陷清单

> 优先级：P0=数据/安全红线；P1=影响核心承诺或可复现的功能错误；P2=重要但可延期；P3=体验/一致性。

### P1（建议发布前修复，共 5 项）

**P1-1 自动文件级还原会强制加回“用户已禁用”的第三方 bundle（违反设计 12.4）**
- 位置：`src/Loom.Core/LoomService.cs:582-599`（`RestoreAsync` 传 `Auto=true, Force=true`）；`RestorePlanner.Create` 不区分“用户禁用”（`RestorePlanner.cs:51-69` 合并所有缺失的非基线 bundle）。
- 影响：更新后用户手动禁用/清理过的插件，在自动还原时被重新启用；check 层虽把其标为 `I_BUNDLE_DISABLED` 且不进 `RestoreCandidates`，自动路径却绕过该约束，正是审核 P0-5 要避免的“工具跟用户对着干”。
- 复现：托盘 Tick 场景（`.qa-accept/tick-2dff828b/data3`）：恢复特征 + 用户依赖仍在 → 自动还原后 bundles 含 `dshmarket`、`dsh-plugin-wallpaper-engine`、`dsh-whale-widget`，与 A14 check 的“用户禁用不候选”结论矛盾。
- 建议：自动还原改用 `Force=false` 并让 Planner 接收 `CheckResult`（只应用 RestoreCandidates + 明确的官方可选）；或给 Planner 增加 `RespectUserDisabled` 开关，自动路径只补“依赖+包都不在但快照有”的可判定项；`--force` 才恢复全部。

**P1-2 自动快照指纹不一致 → 每 15s 重复快照（A02 FAIL）**
- 位置：`LoomService.cs:702-707`（`FingerprintOfProfile`：packageJsonText/lock/patch/bundles）与 `LoomService.cs:902-909`（`FingerprintOfManifest`：appVersion/dshVersion/bundles/FileSha256/lock/patch）算法不同；`MaybeAutoSnapshotAsync`（`LoomService.cs:658-700`）用前者与后者保存值比较，**永远不相等**。
- 影响：DSH 运行时每个 Tick（15s）都会写一份新快照，磁盘/IO 抖动、保留策略频繁淘汰；冻结 pre-update 虽受保护，但正常基线会被快速冲掉，长期运行可能耗尽配额。违反 A02“不重复”与设计 8.2“仅变化才写”。
- 复现：Tick 场景无 profile 变化，第 2 个 Tick 快照 1→2（`evidence/tick/tick.log`）。
- 建议：统一为同一指纹函数（建议 `FingerprintOfManifest` 风格的稳定字段），或快照成功后保存 `FingerprintOfProfile`（采集自同一 ProfileState）；补回归测试 `AutoSnapshotIsNotRepeatedWhenProfileDidNotChange`。

**P1-3 `restore --dry-run` 与失败/取消的 check/restore 不写 journal 终止行 → doctor 永久报“存在未完成操作”**
- 位置：`LoomService.cs:1136-1160`（DryRun 在 `scope.Journal.Append(Done)` 之前 return）；`LoomService.cs:1033-1051`（check catch 不写 journal）；`LoomService.cs:1267-1300`（restore catch 不写 journal）；消费方 `LoomService.cs:1436-1442`（doctor `unfinished-journal`）。
- 影响：任意一次 `restore --dry-run`（文档推荐的高频操作）都会让 doctor 持续 unhealthy（真实环境实测：第二次 doctor exit 2）；未完成 journal 是设计 7.3 的崩溃恢复依据，语义被污染。
- 建议：所有出口（成功/失败/取消/演练）统一 `journal.Append(..., "done|failed|cancelled")`；dry-run 用独立 status（如 `dry-run`）并让 `HasUnfinishedOperation` 视其为终态；doctor 只对“真正未完成”报警；补测试。

**P1-4 损坏的 compatibility.json 会让整单 restore 校验失败并回滚（A23 目标达成但恢复被阻断）**
- 位置：`RestoreService.cs:500-504`（`VerifyApplied` 对“存在但不可解析的 compatibility.json”无条件报错）与 `RestorePlanner.cs:392-403`（计划已明确 `SkipCompatibility`，不覆盖坏文件）。
- 影响：profile 中存在历史损坏豁免文件时，恢复流程无法完成任何其它修复（例如 agent-team/依赖/patch），全部回滚；用户必须先手工修复 compatibility.json。与设计“rewritable:false → 不覆盖、提示手工修复”不一致。
- 复现：`.qa-accept/798e4a4f…` A23 场景：restore exit 1，消息“写入后校验失败：compatibility.json 不可解析”，已写 bundle 被回滚；坏文件字节保持不变。
- 建议：`VerifyApplied` 只校验“本次计划要写的”文件；对被计划跳过/保留的文件不做可解析性校验（或降级为警告）；补测试“damaged compat + other changes → restore succeeds and leaves the file untouched”。

**P1-5 `Severity.Info` 的用户改动仍会把更新后状态判成 Blocked（误报“需人工处理”）**
- 位置：`LoomService.cs:601-607`（`DetectVersionChangeAsync` 用 `result.Issues.Count > 0` 判定 Blocked）；对比 `LoomService.cs:965`（状态汇总已正确过滤 `Severity != Info`）。
- 影响：dshVersion 变化后，用户自己的禁用/新增/未安装（Info 级说明）会导致 phase=Blocked、托盘黄灯“插件需要人工处理”，而实际无需处理；与 A15/A06 的“用户改动不应造成告警”意图冲突。
- 建议：与 `RunCheckAsync` 一致，只统计 `Severity != Info`；`RequiresManualReview` 已按强证据计算，可直接复用。
